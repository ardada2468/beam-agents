`.traces` carries `TraceEvent` records — spans for the activation and for each
model call, tool call, and staged intent inside it. Attributes follow the
OpenTelemetry GenAI semantic conventions, and `trace_id`/`span_id` use the W3C
trace-context wire sizes so an exporter passes them through untranslated.

## The shape of one trace

A trace is scoped to `(entity_key, seq)`, not to a single `process()` call. A
suspension and its later resume run under the same `seq`, so the resume
recomputes the same `trace_id` with nothing carried on the wire, and its
activation span hangs under the first attempt's rather than starting a second
trace.

{/*
  The nesting is the part prose keeps failing to convey. Every child event's
  `parent_span_id` is *the attempt's* activation span, and a resume is itself a
  child of the first attempt — so any activation that suspends is a two-level
  tree, not the flat sequence a list of event names implies. That distinction
  is the first thing anyone writing a query against `parent_span_id` needs.

  Geometry notes, since the numbers here are hand-placed:

  - The tree is authored at 620 user units wide because the docs article column
    is ~630 CSS px. A 1000-unit diagram would either scroll on a 1440px screen
    or scale its 11px type down to something unreadable.
  - Spines sit inside their parent box's horizontal span (x=28 under the root,
    x=72 under the resume) so a child visibly hangs *under* its parent, and
    they carry no arrowhead: the direction is asserted by the short horizontal
    branches, which is where parent/child actually gets claimed.
*/}

## What a failed activation leaves behind

Traces show the atomic-commit rule from the outside: a committed activation
emits its whole span set, while a failed one emits a single `ERROR` event,
because the spans it staged are discarded along with its other effects.

{/*
  This asymmetry is the most missable property of the stream, and it decides
  whether a dashboard built on `.traces` is honest: a query counting LLM_CALL
  events is counting *committed* model calls only. The calls a failed
  activation made are gone with everything else it staged.

  Both branches share a layout so the eye reads the difference rather than
  re-parsing two unrelated pictures. The load-bearing detail is that the failed
  branch's `staged spans` box has nothing leaving it — the ERROR record comes
  from a `FailureContext` built out of position scalars (step index, the name
  of the last staged event, counts), never from the staged effects, which is
  what keeps "a failed activation commits nothing" true for telemetry too.
*/}

The `otlp://` sink is valid only for `traces_to`. It is a best-effort tap that
drops on delivery failure by contract, and intents and errors are
correctness-bearing streams that need a lossless sink.
