Side effects execute **outside** the pipeline, in a separate service:
`intents → dedup → execute → results → re-injection`. The effector shipped here
is a reference implementation, not a hosted product, and it is installed from
the `effector` extra.

{/*
  `docs/effector.md` draws this whole architecture as one line of box-drawing
  characters. The line is accurate, but it flattens the two things that make
  the design work — that the effector sits on the far side of a process
  boundary, and that the dedup store is what a redelivery hits *instead of*
  the tool — into arrows that look like every other arrow.

  So: a horizontal rule for the boundary, crossed exactly twice (out on
  `.intents`, back on the results topic); the effector's phases stacked in
  execution order below it; and the redelivery drawn as its own inbound arrow
  that terminates at the dedup store and never reaches the tool.

  The rule is horizontal rather than vertical because the coordinate space is
  620 units wide — matching this site's ~630px prose column, so the 11px
  labels render at 11px instead of being scaled down — and a vertical split
  would leave neither side wide enough for `UUID5(ENTITY_KEY, SEQ,
  STEP_INDEX)`, which is the one string in this drawing that has to be exact.

  Conventions are the landing-page pipeline diagram's: `.intents` carries the
  intents stream colour, and the leg that leaves through the message bus and
  comes back is dashed.
*/}

Read the guarantees section below carefully. The honest statement is bounded:
duplicates are bounded to the crash window between a tool's effect and its
durable completion record, and true exactly-once requires tools that are
idempotent on `intent_id`. The end-to-end semantics gate exercises exactly that
— SIGKILLed effector workers, a killed TaskManager, and a full replay over
10,000 events.
