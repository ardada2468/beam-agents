## Why

The runtime has never shipped. `pyproject.toml` still carries the scaffolding placeholder `version = "0.0.0"` ([pyproject.toml:3](../../../pyproject.toml:3)), the repository has zero git tags, there is no `CHANGELOG.md`, and no workflow builds or publishes a distribution — the four workflows under `.github/workflows/` ([ci](../../../.github/workflows/ci.yml), [integration](../../../.github/workflows/integration.yml), [quality](../../../.github/workflows/quality.yml), [nightly](../../../.github/workflows/nightly.yml)) mirror the testing tiers and nothing else. Meanwhile the project already talks about releases as if they exist: the semantics gates "gate every release and never get skipped" ([project.md:75](../../project.md)), and latency-budget regressions "are release blockers" ([project.md:111](../../project.md)). With the M2–M4 gate work landing — the effectively-once e2e gate, the adapter conformance matrix, Flink CI, and the docs site — everything that should *gate* a release exists or is in flight, but there is no release for it to gate: no way for a user to `pip install beam-agents`, no statement of what a version number promises, and no record of what changed between versions.

Cutting 0.1.0 requires three missing pieces, which this change delivers together because they are one contract: **packaging and publish automation** (a tag-triggered workflow that builds and publishes verified distributions), a **pre-1.0 versioning policy** (what a breaking change is for this project and which version component it moves), and **changelog automation** (a mechanism that turns the repo's existing one-merged-commit-per-OpenSpec-change discipline, [project.md:92](../../project.md), into release notes without archaeology at tag time).

## What Changes

- **Release workflow (`release.yml`, tag-triggered).** Pushing an annotated `vX.Y.Z` tag runs a new fifth workflow: build sdist + wheel via a new `make build` target, verify the artifacts (tag matches `[project].version`, wheel ships `py.typed` and the committed `_protos` bindings, no `tests/` leakage, console script and extras metadata intact), re-run the offline gates on the tagged ref, then publish to PyPI via **trusted publishing** (OIDC through a GitHub `pypi` environment — no long-lived API token, the same no-static-credential stance nightly already takes with Workload Identity Federation, [nightly.yml:53](../../../.github/workflows/nightly.yml:53)) and create a GitHub Release whose body is that version's changelog section. Publish is unreachable unless build, verification, and gates all pass.
- **Pre-1.0 versioning policy.** `0.MINOR.PATCH` with an enumerated compatibility surface: the public API re-exported from `beam_agents/__init__.py`, the wire/state protos and `state_schema_version` discipline, the `beam-agents-effector` CLI ([pyproject.toml:48](../../../pyproject.toml:48)), the published extras names (`effector`, `langgraph`, `otlp`, [pyproject.toml:20](../../../pyproject.toml:20)), and the supported Python/runner matrix ([pyproject.toml:7](../../../pyproject.toml:7)). Pre-1.0, breaking changes to that surface bump MINOR (with the break called out in the changelog); PATCH releases contain fixes only. The policy lives in `docs/releasing.md` and is machine-checked at release time: a PATCH tag with breaking- or feature-typed changelog fragments fails the release.
- **Changelog automation via towncrier fragments.** Each user-facing change adds a fragment under `changelog.d/` named after its OpenSpec change folder (`<change-name>.<type>.md`), making the changelog entry part of the same reviewed diff as the code — the natural continuation of "one merged commit = one archived OpenSpec change." A closed fragment-type registry (`breaking`, `added`, `changed`, `fixed`, `docs`, `internal`) maps types onto the versioning policy. A pre-commit/CI check requires a fragment whenever `src/` changes (same enforcement pattern as the existing `openspec-change-required` hook, [.pre-commit-config.yaml:33](../../../.pre-commit-config.yaml:33) / [scripts/check_openspec_change.sh](../../../scripts/check_openspec_change.sh)); `internal` fragments satisfy the check without rendering into the changelog. `make changelog` runs `towncrier build` to assemble the version's `CHANGELOG.md` section and consume the fragments.
- **Version bump discipline.** The version stays statically single-sourced in `pyproject.toml` (no VCS-derived versioning; see design D1). A release is a reviewed PR that bumps `version`, refreshes `uv.lock` (whose `beam-agents` entry records the same version, [uv.lock:277](../../../uv.lock:277)), and runs `make changelog`; the tag lands on that squash-merged commit.
- **Tooling plumbing.** A new `release` dependency group (towncrier), new Makefile targets `build` and `changelog` (preserving the "Makefile is the CI/local contract" rule, [CONTRIBUTING.md:20](../../../CONTRIBUTING.md:20)), `scripts/check_wheel.py` and `scripts/check_release.py` for the artifact/policy verifications, and a one-time curated 0.1.0 backfill of `CHANGELOG.md` from the nine archived OpenSpec changes.

## Capabilities

### New Capabilities

- `release-process`: how a version of `beam-agents` gets built, verified, gated, tagged, and published — the single-source version rule, the tag-triggered trusted-publishing workflow, the distribution-content checks, the pre-1.0 versioning policy and its machine-checked mapping from changelog fragment types to version components.
- `changelog-automation`: the changelog contract — per-change towncrier fragments named after OpenSpec change folders, the closed fragment-type registry, the fragment-required enforcement for `src/` changes, and release-time assembly into `CHANGELOG.md`.

### Modified Capabilities

None. `repo-scaffolding` ([openspec/specs/repo-scaffolding/spec.md](../../specs/repo-scaffolding/spec.md)) is the nearest existing capability, but none of its requirements change: its workflow requirement mandates the four testing-tier workflows without excluding others, and `release.yml` is an event-driven (tag-push) workflow outside the tier mirror; its Makefile-contract requirement is *upheld*, not altered — the release workflow's build/changelog steps go through new `make` targets exactly as that contract demands; and its dependency-group and pre-commit requirements enumerate what must exist, which the additive `release` group and `changelog-fragment` hook leave intact. All new obligations are stated as requirements of the two new capabilities rather than edits to scaffolding's contract.

## Impact

- **Depends on:** the release-gating suites this process fronts — `add-effectively-once-e2e-gate` (C16) and `add-adapter-conformance-matrix` (C22), which are the "gate every release" semantics tier ([project.md:75](../../project.md)) the release checklist requires green — plus the sibling batch items `add-flink-minicluster-ci` (C23, keeps the Flink legs of those gates runnable in CI so a green `integration` check means what the checklist assumes) and `add-docs-site` (C24, the published documentation a first public release points users at; the `docs` dependency group is empty today, [pyproject.toml:101](../../../pyproject.toml:101)).
- **New code:** `.github/workflows/release.yml`; `scripts/check_wheel.py` (distribution-content verification) and `scripts/check_release.py` (tag/version/lock agreement + fragment-type-vs-bump policy check); `changelog.d/` with the towncrier type registry; `CHANGELOG.md` (0.1.0 backfill); `docs/releasing.md` (policy + release checklist); `tests/release/` unit tests for both check scripts (driven against synthetic wheels/fragments, offline, no new pytest marker needed).
- **Modified code:** `pyproject.toml` (`[tool.towncrier]` config, `release` dependency group, and — at release time only — the `version` field); `uv.lock` (lockstep with the version bump); `Makefile` (`build`, `changelog` targets added to the [.PHONY roster](../../../Makefile:7)); `.pre-commit-config.yaml` (the `changelog-fragment` local hook); `CONTRIBUTING.md` (fragment authoring + release sections). No `src/` changes: the runtime is untouched, and the wheel already packages `src/beam_agents` wholesale under hatchling ([pyproject.toml:117](../../../pyproject.toml:117)) including `py.typed`.
- **CI/build:** `release.yml` is a new, non-required, tag-triggered workflow (it can never block PRs; it blocks *publishing*). The fragment check rides the existing `quality` pre-commit step ([quality.yml:33](../../../.github/workflows/quality.yml:33)) — no new required check. PyPI-side setup (project registration, trusted-publisher binding to `release.yml` + the `pypi` environment) is a documented one-time task.
- **Gates:** `make lint`, `make type`, `make test-unit` (the new script tests are plain unit tests and count toward coverage), coverage ratchet, `uv run pre-commit run --all-files`, `openspec validate add-0-1-0-release --strict`; plus the release-only gates this change itself introduces (artifact verification and the offline gate re-run inside `release.yml`).
