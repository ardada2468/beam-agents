## Why

The reference effector closed the effects loop — `.intents → outbox → effector → results → re-injection` — but the loop's only security boundary today is transport-level access to the broker. Three gaps follow, each grounded in shipped code:

1. **No application-level authenticity.** The effector executes whatever parses as a `ToolIntent` off the outbox topic ([service.py:255](../../../src/beam_agents/effector/service.py:255)). Anything that can produce to that topic — a misconfigured producer, an over-permissioned service, a compromised credential — can mint an intent for any registered `side_effect=True` tool with attacker-chosen `args_json`, and the effector will run it against real external systems. The dedup store ([dedup.py:69](../../../src/beam_agents/effector/dedup.py:69)) is no defense here: it suppresses *duplicates* of an `intent_id`, and a forged intent simply carries a novel one.
2. **No broker-auth surface.** The Kafka adapters construct clients with nothing but bootstrap servers and a group id — [sources.py:139](../../../src/beam_agents/effector/sources.py:139), [sinks.py:123](../../../src/beam_agents/effector/sinks.py:123), and the outbox writer's hardcoded `producer_config` at [write_intents.py:86](../../../src/beam_agents/actions/write_intents.py:86) — so a deployment that wants SASL/mTLS has no way to configure it. Pub/Sub gets IAM via Application Default Credentials, but the least-privilege topic/subscription role split is documented nowhere.
3. **Secrets ride on env/config with leak paths.** A `redis://:password@host` dedup URI leaks its credential into `EffectorConfigError` messages ([config.py:88](../../../src/beam_agents/effector/config.py:88) interpolates the raw URI), into the default dataclass `repr` of `EffectorConfig` ([config.py:106](../../../src/beam_agents/effector/config.py:106)), into stderr at startup ([\_\_main\_\_.py:152](../../../src/beam_agents/effector/__main__.py:152)), and into `argv` (visible in process listings) when passed as a flag. And nothing states the most important rule of all: `args_json` is persisted in keyed state, written to a broker topic, and re-encodable into dead letters — a secret placed in tool arguments is a secret copied everywhere.

This change adds intent signing (pipeline signs, effector verifies before anything else), a configuration surface for broker authentication, and a secret-handling pass that closes the leak paths and documents the pattern.

## What Changes

- **`ToolIntent` gains a signature envelope** — `signature_scheme` (enum), `signing_key_id` (string), `signature` (bytes) — as additive fields taking the next free field numbers, above every existing field ([beam_agents.proto:40](../../../protos/beam_agents.proto:40)). The signature is HMAC-SHA256 over the deterministic serialization of the intent with the three signature fields cleared. Like `intent_id` ([agent.py:43](../../../src/beam_agents/core/agent.py:43)), the schema only transports it; nothing is computed in the proto layer. A pre-signature intent decodes with an unspecified scheme and reads as unsigned.
- **New Beam-free `src/beam_agents/intent_signing.py`** (stdlib `hmac`/`hashlib` only, the `hitl.py` precedent): `sign_intent`, `verify_intent`, and a keyring type mapping `key_id → key bytes` loaded from a file or environment reference — the config carries the *reference*, never the key material. HMAC and uuid5-deterministic intent IDs together mean a retried bundle re-signs to byte-identical wire messages, so the outbox path stays replay-deterministic.
- **The pipeline signs at the outbox writer.** `WriteIntents` ([write_intents.py:237](../../../src/beam_agents/actions/write_intents.py:237)) accepts an optional signer spec; `_SerializeIntent` ([write_intents.py:224](../../../src/beam_agents/actions/write_intents.py:224)) stamps the signature fields before serializing. Staged intents in keyed state (`ctx.act` / [context.py:590](../../../src/beam_agents/core/context.py:590)) are untouched — the signature is a transport property, and key material is loaded worker-side in `DoFn.setup()`, never pickled into the pipeline graph.
- **The effector verifies before every other phase.** A new verification step precedes even `refuse_expired` ([service.py:260](../../../src/beam_agents/effector/service.py:260)): an unauthenticated message must not drive *any* behavior, including publishing an `EXPIRED` result. Verification failures (tampered, unsigned-under-`require`, unknown key id) go to a configurable dead-letter channel — reusing the dead-letter vocabulary of `REASON_INTENT_DEAD_LETTER` ([dofn.py:127](../../../src/beam_agents/core/dofn.py:127)) — and **never** publish a `ToolResult`, because a `REJECTED` result minted from forged `entity_key`/`intent_id` fields would hand an attacker a lever on the keyed re-injection path. The offset is committed past a dead-lettered delivery so a forgery flood cannot wedge a partition head; a corrupted *genuine* intent fails closed via the pipeline's HITL timer (correctness invariant 6).
- **Verification mode is a rollout dial**: `off` (default; today's behavior), `permissive` (verify signed intents, accept-and-count unsigned ones), `require` (unsigned intents dead-letter). This is what makes unsigned→signed deployable against a topic with retention full of unsigned intents.
- **Broker authentication becomes configurable, and the boundary is stated honestly.** The library cannot *enforce* broker authn — that is the broker's job — so it does two things: threads a transport-security settings block (SASL mechanism, TLS, credential references) into the Kafka consumer/producer constructions on both sides of the topic, and documents the hardening baseline in a new `docs/security.md`: SASL_SSL or mTLS for Kafka with per-principal topic ACLs, Pub/Sub IAM with a least-privilege role matrix (pipeline: publish intents, subscribe results/approvals; effector: subscribe intents, publish results/approvals/dead-letters).
- **Secret-handling review lands as code plus doctrine.** Code: URI userinfo is redacted in every error message and in `EffectorConfig`'s `repr`; broker/dedup credentials are supplied by env/file reference rather than URI embedding; the signing keyring follows the same rule. Doctrine (`docs/security.md`): secrets MUST NOT appear in intent payloads or tool arguments — tools resolve their own credentials effector-side (the `IntentInfo` idempotency pattern in [docs/effector.md](../../../docs/effector.md) already shows the shape) — and provider/broker/store credentials flow from a secret manager into the effector's environment, never through `argv`. Enforcement by lint was considered and rejected: scanning `args_json` for secret-shaped strings is unreliable in both directions (design D8); the reliable mechanism is structural.

## Capabilities

### New Capabilities

- `effector-security`: intent signing at the outbox writer, signature verification as the effector's first phase, dead-letter semantics for verification failures, the `off`/`permissive`/`require` rollout modes, broker transport-security configuration by credential reference, secret redaction in config errors/reprs, and the documented security baseline (broker authn hardening, least-privilege roles, secrets-never-in-args).

### Modified Capabilities

- `wire-schemas`: `ToolIntent` grows the three additive signature fields (`signature_scheme`, `signing_key_id`, `signature`) at the next free field numbers; the ToolIntent requirement is extended to cover their round-trip and the unsigned-decode compatibility of pre-signature intents. See [../../specs/wire-schemas/spec.md](../../specs/wire-schemas/spec.md).

## Impact

- **Depends on:** C15 [`add-reference-effector`](../add-reference-effector/proposal.md) — this change hardens the service, sources/sinks, dedup, and config surfaces that change shipped (`src/beam_agents/effector/`), and extends its `effector-service` phase order with a verification step. When both changes archive, the effector-service requirement "Each intent is processed in the order refuse-expired, claim, execute, complete, publish, commit" reads verify → refuse-expired → …; the delta here states verification's position explicitly so the two specs compose without contradiction.
- **New code:** `src/beam_agents/intent_signing.py` (Beam-free, stdlib-only signer/verifier + keyring loading); `docs/security.md`.
- **Modified code:** `protos/beam_agents.proto` + committed regenerated `src/beam_agents/_protos/` (diff-clean regen gate applies; additive fields, no `state_schema_version` bump); `src/beam_agents/actions/write_intents.py` (optional signer spec, key load in `setup()`); `src/beam_agents/effector/config.py` (verification mode, keyring reference, transport-security block, URI redaction, non-leaking `repr`); `src/beam_agents/effector/service.py` (verification phase, dead-letter publish, new metrics counters); `src/beam_agents/effector/sources.py` / `sinks.py` (Kafka security settings threading); `src/beam_agents/effector/__main__.py` (new flags/env vars, redacted startup errors); `docs/effector.md` (pointer to the security doc and the new phase order).
- **CI/build:** no new dependencies — HMAC-SHA256 is stdlib, which is a deciding factor in design D2. Proto regen must stay diff-clean; golden-blob compat tests gain a signed-intent blob and an unknown-field verification case.
- **Gates:** offline unit tests for signing/verification/redaction (no docker); a `semantics and not integration` addition to the effectively-once gate — with `require` mode on, a tampered or forged intent stream produces zero tool invocations and zero published `ToolResult`s while genuine signed intents still execute exactly once per `intent_id`; `-m integration` covers SASL-enabled Redpanda wiring. Coverage ratchet holds; `make lint`, `make type`, `openspec validate add-effector-security --strict` all clean.
