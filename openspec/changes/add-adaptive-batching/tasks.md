## Revisions

### Revision 1 — the `ctx.event` widening needed a narrowing accessor, and the Impact section understated its blast radius

`design.md` D4 says the annotation widens to `bytes | list[bytes]` and dismisses the leak-to-`NONE`-users risk as annotation-only. That holds at runtime but not under `mypy --strict`: every existing single-event consumer of `ctx.event` becomes a type error, and 12 of them live outside the Impact section's file list — the three framework adapters, the four `examples/` agents, `benchmarks/_harness.py`, and test helpers.

Casting at each site would have hidden a real question: those consumers are genuinely undefined under `ADAPTIVE`. So `ActivationContext` gained a third accessor, `single_event: bytes`, which returns the payload on the per-event path and raises `TypeError` (naming `ctx.events`) under `ADAPTIVE`. Each consumer moved one expression onto it — behavior-preserving under `NONE`, and an actionable failure instead of a `TypeError` from inside somebody else's framework under `ADAPTIVE`. The adaptive-batching spec's "Batch activations are batch-visible" requirement now names the accessor and carries a scenario for it; `proposal.md`'s Impact section names the extra files.

### Revision 2 — the batch-clock scenario is asserted where the maximum is computed

`tasks.md` 1.3 placed "The batch clock is the latest buffered event time" in `test_context.py`/`test_loop.py`. Neither computes it: `now_ms = max(event_time_ms)` is the DoFn flush path's, because only it holds the buffered *envelopes* (the loop driver and the context receive payload bytes and an already-decided clock). The scenario is asserted in `tests/core/test_dofn_batching.py` — a flush over event times 1000/3000/2000 commits an intent whose `created_at_ms` is 3000 and whose `expires_at_ms` derives from it — which is inside the mutation selection, where the tasks file wanted the flush behavior anyway. The spec text is unchanged.

### Revision 3 — the TTL wipe of `BATCH` is guarded on `ADAPTIVE`

The `stateful-agent-runtime` delta says the TTL fire "SHALL clear all six state specs" and, in the same requirement, that under `BatchPolicy.NONE` "`BATCH` SHALL never be read or written". Clearing is a write, so the two read as contradictory for a `NONE` pipeline. Implemented in favor of the inertness guarantee: `on_ttl` wipes `BATCH` and `FLUSH_TIMER` only under `ADAPTIVE`. Nothing is lost — under `NONE` the buffer is provably empty, so the six-spec scenario ("a key that has accumulated ... buffered events") is only reachable under `ADAPTIVE`, where the wipe does happen. `tests/core/test_dofn_ttl.py` now pins the `NONE` half (the callback is handed both handles and touches neither) and `tests/core/test_dofn_batching.py` the `ADAPTIVE` half. The spec text is unchanged; this note records the reading.

### Revision 4 — the metric surface is eleven counters, not ten

The `runtime-metrics` delta enumerated ten counters, omitting `longterm_upserts` — which `add-longterm-memory` added to `observability/metrics.py` without its own `runtime-metrics` delta, so this change's delta was drafted against a stale list. Corrected to eleven, with `longterm_upserts` in its declared position. The distribution count (seven, including the new `batch_size`) was already right.
