## Why

The runtime activates the agent once per event, unconditionally. For the target workloads — IoT reaction, fraud triage, anomaly response — hot keys arrive in bursts, and a burst of twenty readings for one sensor buys twenty LLM round-trips where one activation over the whole burst would reach the same decision at a twentieth of the cost and latency. The architecture has reserved the mechanism for this from the start: `FLUSH_TIMER` (REAL_TIME — adaptive batching only) is named in the project constitution ([project.md:53](../../project.md)), and `add-stateful-dofn-runtime` explicitly deferred it ("`FLUSH_TIMER` / adaptive batching (deferred)", [design.md:24](../add-stateful-dofn-runtime/design.md)). Nothing else exists yet: there is no `BatchPolicy` type anywhere in the codebase, [dofn.py:199](../../../src/beam_agents/core/dofn.py:199) declares exactly five state specs and two timers, and `ActivationContext.event` ([context.py:404](../../../src/beam_agents/core/context.py:404)) is always a single `bytes` payload. This change fills that reserved slot.

Batching an *agent* is harder than batching a map function because an activation can suspend mid-flight awaiting a tool result or approval. The interaction between a buffered batch and the suspension machinery is currently undefined behavior waiting to happen; this change defines it, and per the roadmap the definition is **whole-batch suspension**: the entire batch's continuation suspends and resumes together.

## What Changes

- **`BatchPolicy` enum, opt-in on `AgentConfig`.** `BatchPolicy.NONE` (default) preserves today's per-event semantics exactly; `BatchPolicy.ADAPTIVE` enables per-key buffering, configured by two new knobs — `max_batch_size` (size-threshold flush) and `max_wait_ms` (processing-time flush) — validated at `AgentConfig` construction ([transform.py:395](../../../src/beam_agents/core/transform.py:395)) like every other knob.
- **A sixth state spec and a third timer.** `BATCH` (`BagStateSpec` of `AgentEnvelope`, deterministic proto coder — no pickle) buffers event elements per key; `FLUSH_TIMER` (REAL_TIME) enforces `max_wait_ms`. Both are declared unconditionally alongside the existing topology ([dofn.py:199](../../../src/beam_agents/core/dofn.py:199)); under `NONE` neither is ever touched.
- **Per-key buffering with two flush triggers.** Under `ADAPTIVE`, an `external_event` element appends to `BATCH` (no activation, no `SEQ` increment); `tool_result`/`approval` elements never buffer. The buffer flushes into one activation when it reaches `max_batch_size` (inline, in `process()`) or when `FLUSH_TIMER` fires `max_wait_ms` of processing time after the first buffered event — armed on the empty→non-empty transition, cleared on flush, tested with `TestStream` processing-time advances, never `sleep()`.
- **Batch-visible activations: `ctx.event` is a list.** A flush runs one activation whose `ActivationContext.event` is a `list[bytes]` (annotation widens to `bytes | list[bytes]`); a new `ctx.is_batch` property and a uniform `ctx.events` tuple accessor make detection explicit. The list shape is fixed by policy, not by batch size — a single-element flush still presents a one-element list, so an `ADAPTIVE` agent handles exactly one type. Under `NONE`, `ctx.event` remains `bytes`, byte-for-byte.
- **One activation per flush.** A committed flush consumes exactly one `SEQ`, mints intent IDs from `(key, seq, step_index)` as today, keys the replay cache by the same `(key, seq)` scope, and runs `run_activation` ([loop.py:149](../../../src/beam_agents/core/loop.py:149)) unchanged. Its activation clock is `max(event_time_ms)` over the batch — a pure function of buffer contents, so a retried flush bundle re-reads the same committed bag and reproduces byte-identical intents with zero extra provider calls.
- **Whole-batch suspension — now DEFINED behavior.** A batch activation that returns `Suspend` ([agent.py:90](../../../src/beam_agents/core/agent.py:90)) persists one `Continuation` covering the entire batch; the resume runs once, at the batch's `seq`, and completes or re-suspends for the whole batch. There is no per-element suspension and no partial resume. While a continuation is live, both flush triggers **defer** (the buffer keeps absorbing events); when the suspension resolves — resume commit, or HITL `Deny`/`Drop` in [on_hitl](../../../src/beam_agents/core/dofn.py:666) — a non-empty buffer's `FLUSH_TIMER` is re-armed to fire promptly, so a deferred batch never needs a second activation inside one element's `process()` call.
- **Fail-closed batch failure and GC.** A failed or timed-out flush dead-letters every buffered envelope to `.errors` and clears the buffer (a poison batch cannot wedge the key in a retry loop); a hard buffer cap dead-letters overflow explicitly rather than growing state silently; `TTL_TIMER` GC wipes `BATCH` with the other five specs and reports wiped buffered events, mirroring `ttl_wiped_suspension`.
- **Observability.** Three new counters (`events_buffered`, `batch_flushes_size`, `batch_flushes_timer`) and one new distribution (`batch_size`) under `beam_agents.runtime`; batch flush activations stamp `beam_agents.batch.size` / `beam_agents.batch.trigger` attributes on their activation trace.

## Capabilities

### New Capabilities

- `adaptive-batching`: the `BatchPolicy` configuration surface, per-key buffering, the two flush triggers (size threshold and `max_wait_ms` via the processing-time `FLUSH_TIMER`), batch-visible `ctx.event` list semantics, one-activation-per-flush seq/intent/replay-cache accounting, whole-batch suspension and resume, flush deferral while suspended, and the fail-closed failure/overflow paths.

### Modified Capabilities

- `stateful-agent-runtime`: the state/timer topology grows to six specs and three timers (`BATCH`, `FLUSH_TIMER`); element routing gains the `ADAPTIVE` buffering branch for `event` elements; the TTL wipe covers the sixth spec and reports wiped buffered events.
- `runtime-metrics`: the fixed metric surface widens by the four batch metrics, and the `.errors` reason vocabulary that `agent_errors` closes over gains `ttl_wiped_batch` and `batch_buffer_overflow`.

- **CI/build:** no new dependencies; all new tests run offline (no docker) with `TestStream` scripted processing-time/watermark advances; the retry-determinism semantics gate is extended to cover a chaos-retried flush bundle.
- **Gates:** `core/dofn.py`, `core/context.py`, `core/loop.py`, `core/transform.py`, and the new `core/batching.py` are all under the `make mutation` gate; expect `mutation-baseline.toml` ceilings to move and document them, per the `add-runtime-metrics` precedent. Coverage ratchet must hold or rise.
