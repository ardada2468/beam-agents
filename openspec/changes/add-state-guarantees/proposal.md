## Why

Correctness invariant 7 stakes a public promise on state evolution: "Pipeline `--update` compatibility: additive proto changes only; breaking changes require `state_schema_version` bump + lazy migration + golden-blob compat test" ([project.md:48](../../../openspec/project.md:48)). The sibling change `add-state-schema-migration` (C32) builds the machinery behind that sentence — the version registry, the lazy migration hooks, the golden-blob movement rules. What still does not exist is the promise itself, stated anywhere a user can read it, and any evidence that `--update` actually works.

Both halves of that gap are real today:

- **The guarantee is folklore, not a contract.** The additive-only rule lives in a proto file comment ([beam_agents.proto:12](../../../protos/beam_agents.proto:12)), a coder docstring ([coders.py:1](../../../src/beam_agents/core/coders.py:1)), and `project.md`. Nothing tells an operator which changes are safe to ship over a running Dataflow job, which require a migration release, and which can never be made — and nothing distinguishes what beam-agents *promises* (state written by release N is readable by N+1) from what merely happens to work (skipping releases, cross-version byte-identity).
- **`--update` has never run.** The golden-blob suite ([test_schema_compat.py:1](../../../tests/core/test_schema_compat.py:1)) proves committed v1 bytes decode in-process with current bindings, and the conformance matrix's `restart_mid_suspension` cell ([_spec.py:251](../../../tests/conformance/_spec.py:251)) proves a suspension survives a same-version pipeline restart. Neither exercises the thing invariant 7 is named after: Dataflow's job-replacement compatibility check and the handoff of live keyed state — a `Continuation` mid-suspension, a populated `MemoryBlob` — from a job running one release to a job running the next. The nightly `dataflow` job ([nightly.yml:34](../../../.github/workflows/nightly.yml:34)) exists for exactly this class of test, and today it runs an empty selection: no test in the repo carries the `dataflow` marker, which is why `make test-dataflow` tolerates pytest's no-tests-collected exit ([Makefile:63](../../../Makefile:63)).

An `--update` incompatibility is the worst kind of defect for this runtime's target users: it is invisible until someone tries to upgrade a long-running production job with money-moving state in flight, at which point the choice is to abandon the upgrade or abandon the state. This change writes down the guarantees and stands up a nightly test that catches a broken promise the night it is introduced, not the quarter it is deployed.

## What Changes

- **A published state-compatibility policy: `docs/state-compat.md`.** The document states, in RFC-2119 terms, what beam-agents promises across releases: state blobs written by release N are readable by release N+1 (directly for additive changes, via C32's lazy migration for versioned ones); the keyed-state wire format is exactly `SerializeToString(deterministic=True)` of the schema protos ([coders.py:73](../../../src/beam_agents/core/coders.py:73)) with no framing, so proto wire-compatibility rules govern; and Dataflow `--update` is supported between adjacent releases. It contains a compatibility table classifying every change class an author can make — adding an optional proto field, adding an enum value, adding a new state spec, removing/renumbering/retyping a field, changing the coder encoding, renaming transforms or state spec ids, bumping `state_schema_version` with a migration — each with three columns: is old state readable, is `--update` safe, and what the author must do. It also names the compatibility surface people forget: `RunAgent`'s internal transform names and the state spec ids and coder types in `core/dofn.py` are part of the `--update` contract, because Dataflow's compatibility check keys carried-over state by step and state id.
- **A nightly `--update` compatibility gate on real Dataflow: `tests/dataflow/test_update_compat.py`** (marked `dataflow` + `slow`), the first test in the repo's `dataflow` tier. The gate launches a small streaming pipeline **at the previous released version** (installed from PyPI into a dedicated venv), drives events that leave live keyed state behind — one key suspended mid-activation awaiting an approval (a persisted `Continuation` + `PENDING` intent), one key with populated working memory (`MemoryBlob`) — then replaces the job in place with `--update` **at the current head** (wheel built from the checkout), and asserts from the outside that the state survived: the suspended key resumes and completes when its approval is injected post-update, the memory key's next activation reads back what was written pre-update, and a fresh key behaves normally. A failed Dataflow compatibility check (replacement job goes to `FAILED` while the old job keeps running) is reported as a compatibility failure — the exact defect class this gate exists to catch — distinct from infrastructure failures.
- **A two-interpreter harness: `tests/dataflow/_update/`** (test-only, never re-exported). One self-contained launcher pipeline module written against the public API only (`RunAgent`, `AgentConfig`, the packaged `FakeLLM` at [fake.py:128](../../../src/beam_agents/model/fake.py:128)) and executed by both interpreters, so both job graphs come from identical source; a version resolver that discovers the latest beam-agents release on PyPI and provisions the previous-version venv; Pub/Sub topic/subscription provisioning under a unique run id; deadline-driven pollers for job state and output (no sleep-based correctness); and teardown that force-cancels both job ids and deletes every provisioned resource on success, failure, and timeout, plus a pre-run sweeper that cancels leaked jobs from prior crashed runs by label and age.
- **Bootstrap before the first release.** The package is version `0.0.0` and unreleased ([pyproject.toml:3](../../../pyproject.toml:3)), so there is no "previous version" on PyPI yet. Until one exists, the gate runs a self-update leg — launch head, `--update` to head — which proves the harness, the Dataflow update mechanics, and that head's job graph is update-compatible with itself (catching nondeterministic transform naming). The cross-version leg arms automatically the night after the first PyPI release; the resolver's fallback is logged loudly so nobody mistakes the bootstrap leg for the real thing.
- **Nightly and Makefile wiring.** The existing `dataflow` job gains the region/temp-bucket repository variables the harness needs and a raised `timeout-minutes`; `make test-dataflow` drops its no-tests-collected tolerance now that the selection is required to be non-empty (matching the stance `test-semantics` already takes); [docs/ci.md:11](../../../docs/ci.md:11) and the release procedure are updated so that a red `--update` gate blocks cutting a release.

## Capabilities

### New Capabilities

- `state-guarantees`: the published cross-release state-compatibility contract — what is promised versus best-effort, the change-class compatibility table, the `--update` compatibility surface — and the nightly Dataflow `--update` gate that proves the promise on a real job with live suspended state and working memory, including its two-version harness, cost/cleanup bounds, and release-blocking status.

### Modified Capabilities

None. `proto-coders` and `wire-schemas` are consumed as-is: this change documents and verifies their existing contracts (deterministic proto serialization, additive-only evolution) without altering any requirement. The migration machinery itself is C32's capability, not this one's.

## Impact

- **Depends on** `add-state-schema-migration` (C32, sibling proposal in this batch): C32 builds the `state_schema_version` bump + lazy-migration machinery and the golden-blob movement rules; this change documents the guarantees that machinery backs and proves the end-to-end `--update` path on Dataflow. The compatibility table's "versioned change" rows cite C32's migration path as the required action. Also depends on the existing golden-blob baseline ([generate.py:1](../../../tests/core/golden/generate.py:1)), `DeterministicProtoCoder` ([coders.py:59](../../../src/beam_agents/core/coders.py:59)), and the nightly Workload Identity Federation setup ([nightly.yml:37](../../../.github/workflows/nightly.yml:37)).
- **New code:** `docs/state-compat.md`; `tests/dataflow/__init__.py`, `tests/dataflow/_update/` (harness package: `pipeline.py` the shared launcher module, `versions.py` PyPI resolution + venv provisioning, `resources.py` Pub/Sub and job lifecycle + sweeper, `poll.py` deadline pollers and failure classification) and `tests/dataflow/test_update_compat.py`; offline (default-tier) companions `tests/dataflow/test_update_compat_harness.py` (unit tests for the harness pieces that can lie: resolver fallback, failure classifier, teardown/sweeper) and `tests/core/test_state_compat_doc.py` (a tripwire asserting the compatibility table keeps a row per spec-enumerated change class). No changes under `src/beam_agents/` — a failure here is a real compatibility defect (or classified infrastructure noise), never a runtime patch smuggled in with the gate.
- **Modified code:** none in `src/`. `tests/dataflow/` is a new directory; existing tests are untouched.
- **CI/build:** `.github/workflows/nightly.yml` `dataflow` job: `timeout-minutes` 30 → 50, new `GCP_REGION` and `GCP_DATAFLOW_TEMP_BUCKET` repository variables passed through to the harness (the job keeps its `vars.GCP_PROJECT_ID` gate and skip-notice behavior). `Makefile` `test-dataflow` loses the `test $$? -eq 0 -o $$? -eq 5` tolerance — an empty `dataflow` selection becomes a deselected gate, not a pending one; without GCP configuration the test *skips* (exit 0), it does not deselect. `docs/ci.md` nightly row updated; `project.md`'s tier note for `-m dataflow` stays accurate as written.
- **Runtime cost:** one streaming job, `--max_num_workers=1`, Streaming Engine, small machine type, budgeted ≤ 35 minutes wall clock inside the 50-minute job window, run once nightly only when GCP variables are configured. Every provisioned resource carries the run id and a `beam-agents-update-compat` label; teardown is unconditional and the sweeper bounds the blast radius of a crashed run to one night.
- **Gates:** the gate itself is release-blocking — the release procedure in `docs/state-compat.md` requires the most recent nightly `dataflow` leg green before tagging, and the test MUST NOT carry `xfail`, `skipif`-on-flake, or retry tolerance. Standard change gates apply: `make lint`, `make type`, `make test-unit` (harness unit tests run offline; the gate module itself skips without GCP env), coverage ratchet unaffected (no `src/` change), `openspec validate add-state-guarantees --strict`.
