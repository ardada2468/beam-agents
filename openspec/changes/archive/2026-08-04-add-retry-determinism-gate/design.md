## Context

Correctness invariants #2 (deterministic intent IDs) and #3 (replay cache: bundle retries incur zero additional provider calls) are the whole effectively-once argument, yet neither is exercised. `project.md` promises a `-m semantics` "retry determinism (chaos wrapper forcing bundle retries: zero extra FakeLLM calls, byte-identical intents)" gate. Today: the `semantics` marker exists, but `make test-semantics` runs only inside the docker-gated `integration` workflow and tolerates exit code 5 — so with no semantics tests written, the gate is vacuously green and lives behind docker it does not need.

**This design was revised after empirical spikes against the actual runtime** (see below) invalidated the original mechanism sketch (a custom fault-injection seam on `_AgentDoFn` plus a two-pipeline-run baseline-vs-chaos harness). Three findings, each confirmed by running real `TestStream` pipelines against `src/beam_agents/core/dofn.py`:

1. **Beam's classic `BundleBasedDirectRunner` already retries a failed bundle with genuine state rollback — no custom retry machinery is needed.** `TransformExecutor.call()` (`apache_beam/runners/direct/executor.py`) retries a bundle that raises during `process()` up to `_MAX_RETRY_PER_BUNDLE = 4` times. Instrumenting `_AgentDoFn._commit` to raise on its first invocation and inspecting `memory.read()` on the retry showed the retry re-reads the exact pre-bundle state (`None`, i.e. nothing from the failed attempt leaked through) and the whole activation re-runs from scratch. This *is* "a chaos wrapper forcing bundle retries" — it already exists in Beam; we only need a hook to make one targeted bundle fail once.
2. **"Zero additional provider calls under retry" is only achievable for a *resumed* activation, not a raw single-shot retry.** `compute_cache_key` bakes in `seq` (`model/replay_cache.py`), and every activation gets a fresh, monotonically-incrementing `seq` committed only once, at the end. Since Beam rolls back *all* keyed state on a failed attempt (confirmed above), a brand-new (never-before-committed) LLM call is unavoidably re-issued to the provider on retry — there is no keyed state anywhere holding a same-`seq` cache entry that hasn't rolled back too. The invariant becomes achievable exactly in the suspend→resume case: `_resume()` reuses `cont.seq` (`core/dofn.py`), and `_commit()` unconditionally writes `cache_blob` even for a `"suspended"` result — so a resumed activation that re-issues the *same* request it (or an earlier resume) already answered reads that request from the `LLM_CACHE` committed at suspend time. Verified end-to-end: an agent that calls the model once, emits an intent, and suspends; then on resume calls the model again with the identical request before completing. With the resume's *own* first commit attempt forced to fail, the retried resume still shows exactly one `cache_hit=false` trace (the original call) and one `cache_hit=true` trace (the resume) — the discarded failed attempt's internal call was *also* a cache hit, so it never touched the provider either. Total real provider calls: 1, regardless of the forced extra attempt.
3. **Assert via the pipeline's own committed `.traces`/`.intents` output, not by reading a shared `FakeLLM` instance's counters through the pipeline.** Beam pickles the DoFn (and closures referencing the provider) for execution; a spike using a module-level shared `FakeLLM` and reading its `call_count` from outside the pipeline gave nonsensical results after Beam's serialization round-trip. This repo's own tests already draw this line correctly: `tests/model/*.py` and `tests/core/test_loop.py` call `run_activation`/`LlmFacade` directly (no Beam pipeline) and read `FakeLLM.call_count`/`calls_for` freely; pipeline-level tests instead assert on the committed `TraceEvent.attributes["beam_agents.cache_hit"]` (already staged by `ActivationContext.call_model` for exactly this purpose) and on `.intents`. The semantics test follows the same split.

These findings eliminate the need for: a test-only hook on `_AgentDoFn` (monkeypatching `_commit` from the test module achieves the same fault injection with zero production-code surface), and a two-pipeline "baseline vs. chaos" comparison harness (asserting against the deterministic cache-key/intent-ID formulas directly, from one chaos-instrumented run, is simpler and sufficient).

## Goals / Non-Goals

**Goals:**
- A reusable chaos helper (`beam_agents.testing.chaos`) that makes exactly one targeted `_AgentDoFn` commit fail on its first attempt, relying on Beam's own bundle-retry mechanics (verified above) to do the actual replay.
- The retry-determinism semantics test: a suspend→resume pipeline where the resume's chaos-forced retry demonstrably adds zero provider calls (via `.traces` cache-hit assertions) and the committed intent is exactly the deterministic `intent_id`.
- Wired as a required, offline `ci` check with no empty-collection tolerance.

**Non-Goals:**
- Making a *first-ever* (uncached) LLM call free on retry — physically unachievable without a rollback-surviving cache the runtime does not have and this change does not add. That is not what invariant #3 claims: "cached path" means already-committed, same-`seq` cache state, which only recurs across suspend→resume.
- Any change to `_AgentDoFn`, `ActivationContext`, or `ReplayCache` production code. The gate is a pure verifier of already-implemented behavior.
- The effectively-once end-to-end gate (induced worker kills) and the state-compat golden-blob gate — separate `-m semantics` changes.

## Decisions

### D1: Fault injection is a monkeypatch from the test module, not a hook on `_AgentDoFn`
`beam_agents.testing.chaos.fail_first_matching_commit(matcher)` is a context manager that replaces `_AgentDoFn._commit` at the class level for its duration, restoring the original on exit. It raises a designated `ChaosBundleFailure` from the *replacement* the first time an `ActivationResult` satisfies `matcher`, then delegates to the original `_commit` for every subsequent call (including Beam's own retry of the failed bundle). This requires no change to production code (`core/dofn.py` stays untouched), eliminating the "test-only surface on production code" risk entirely.
- *Alternative — injected `_pre_commit_hook: Callable | None` on `_AgentDoFn`* (the original design): rejected. Adds permanent test-only surface to production code for no benefit now that a monkeypatch achieves the identical effect with the same verified semantics.

### D2: Rely on Beam's native bundle retry; do not simulate it
Confirmed empirically: `BundleBasedDirectRunner` (used whenever a pipeline sets `StandardOptions.streaming = True`, which this project's ordered per-key `TestStream` tests already require) retries a bundle that raises during `process()`, and keyed state read on the retry reflects the clean pre-bundle value — Beam itself discards whatever the failed attempt staged. The chaos helper therefore does not need to model a rollback (no "discard keyed state, preserve worker-local structures" logic) — there is nothing worker-local to model; Beam's own state backend *is* the mechanism.
- *Alternative — target the portable `FnApiRunner` and its `direct_runner_bundle_repeat` option:* rejected. That option only applies when the pipeline is *not* streaming (`SwitchingDirectRunner` routes streaming pipelines to `BundleBasedDirectRunner`, where `bundle_repeat` has no effect), and this project's ordered multi-element per-key tests require `TestStream`/streaming for correct ordering. The classic runner's own retry-on-exception behavior is the mechanism actually in play.

### D3: The scenario is suspend → resume with a repeated LLM call, not a bare retried single-shot activation
Per finding #2, chaos targets the *resume's* commit specifically (matched via a caller-supplied predicate over `ActivationResult`, e.g. `lambda r: r.status == "completed"` when the test knows only the resume produces a completed result). The test agent: (1) calls the model, stages an intent, suspends; (2) on resume, calls the model again with the identical request, then completes. This is the realistic shape of invariant #3 — a resume that redundantly re-derives context already answered before suspending pays nothing extra, chaos retry or not.

### D4: Assert on `.traces` and `.intents`, not on a shared `FakeLLM` instance read through the pipeline
The harness constructs the pipeline with a per-DoFn-instance `FakeLLM` (via `provider_factory`, same pattern as every existing DoFn test) and makes no attempt to read its counters from the test process. Instead it asserts: exactly one `LLM_CALL` trace with `cache_hit == "false"` (the original call) and exactly one with `cache_hit == "true"` (the resume, whether the retry needed 1 or 2 attempts internally) via `assert_that(out.traces, ...)`; and that `.intents` contains exactly the intent predicted by `intent_id_for(entity_key, seq, step_index)` computed directly from the test's known call sequence. A negative-path unit test (not a full second pipeline run) proves the trace assertion actually detects a broken invariant, by asserting the same helper against a hand-built trace list containing an extra `cache_hit == "false"` and showing the assertion fails.

### D5: Placement
`beam_agents/testing/chaos.py` (new `testing` package, test infrastructure, never re-exported from the root API — same convention as `FakeLLM` living in `beam_agents.model`). The semantics test lives in new `tests/semantics/test_retry_determinism.py`, matching the tier's existing directory convention (`tests/core`, `tests/model`, etc.).

## Risks / Trade-offs

- **[R1] Monkeypatching a class method for the duration of a `with` block is inherently global/process-wide state.** → Mitigation: the context manager restores the original `_commit` in a `finally`, and the semantics test module owns the `with` block scope tightly around the single `pipeline.run()`. Not parallel-test-safe if pytest ever runs semantics tests in threads sharing one process — mitigated by keeping this tier single-process (already how `pytest -m semantics` runs today) and documenting the constraint in the module docstring.
- **[R2] The predicate-based "fail the first matching commit" targeting could accidentally match the wrong activation (e.g., the suspend instead of the resume) if the predicate is too loose.** → Mitigation: the semantics test's predicate is specific (`status == "completed"`, and in this single-key/single-suspend test there is exactly one such commit), and a unit test asserts the helper fails the *first* matching commit and lets every subsequent one (matching or not) through unmodified — the once-not-forever, once-not-zero property from the original spec, retargeted at the predicate rather than "every bundle."
- **[R3] Relying on `BundleBasedDirectRunner`'s retry count (4) being enough / always triggering** is implicit rather than configured. → Accepted: the retry is Beam's own default, unconditional on exception type, and the spike showed it fires reliably; if Beam ever changes this default the semantics test's failure would surface it immediately (a red gate, not a silent pass), which is exactly the fail-loud behavior wanted (§6 exit-5 tolerance removal, same principle applied to this deeper assumption).
- **[R4] Tightening the exit-5 tolerance could red-flag CI if the offline selection is momentarily empty during rollout.** → Mitigation: land the test and the CI wiring in the same change so the selection is non-empty the moment the tolerance is removed.

## Migration Plan

Additive and test-only: (1) add `testing/chaos.py`; (2) add `tests/semantics/test_retry_determinism.py`; (3) add `test-semantics-offline` and wire it into `ci.yml`; (4) update `project.md`. No production code changes, no schema changes. Revert is a straight file removal.
