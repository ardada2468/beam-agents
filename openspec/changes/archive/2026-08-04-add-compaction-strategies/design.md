## Context

The memory facade shipped a complete compaction *seam* with no strategy behind it. `Compactor` is a one-method protocol (`compact(memory)`, [facade.py:58](../../../src/beam_agents/memory/facade.py:58)) that the facade calls at two sites: once when a write crosses the 75% soft cap ([facade.py:256](../../../src/beam_agents/memory/facade.py:256)) and once before rejecting a hard-cap-crossing write ([facade.py:214](../../../src/beam_agents/memory/facade.py:214)), with cap enforcement suspended for the duration so the strategy mutates freely through the guarded API. `ActivationContext` takes a `compactor` and hands it to `Memory` ([context.py:392](../../../src/beam_agents/core/context.py:392)); `run_activation` threads it ([loop.py:162](../../../src/beam_agents/core/loop.py:162)); `_AgentDoFn._activate` passes nothing ([dofn.py:483](../../../src/beam_agents/core/dofn.py:483)). Three facts about the surrounding architecture constrain every design below.

**The hook is synchronous and runs on the bridge event loop.** `compact()` is called from inside `Memory._guarded_write` — that is, in the middle of a `ctx.memory.set/append` call made by the agent coroutine, which is itself running on the async bridge's event loop. A compactor therefore cannot `await` anything: there is no way to reach `ctx.call_model` (an `async def`) from inside `compact()` without blocking the loop the provider call would need to run on. Whatever runs behind the existing hook must be LLM-free by construction.

**Every LLM call must be replay-cached and staged, or determinism dies.** Correctness invariant 3 keys every model call by `sha256(model_id, canonical_json(messages), tools_schema, sampling_params, key, seq)` ([replay_cache.py:73](../../../src/beam_agents/model/replay_cache.py:73)) and requires bundle retries to incur zero provider calls on the cached path; invariant 1 requires all effects — cache inserts and memory writes included — to stage in the activation and commit atomically. `ActivationContext.call_model` ([context.py:469](../../../src/beam_agents/core/context.py:469)) is the one runtime path that satisfies both. A summarizer that talks to the provider anywhere else produces different bytes on retry and commits a divergent `MemoryBlob`.

**TTL fire has no activation.** `on_ttl` ([dofn.py:622](../../../src/beam_agents/core/dofn.py:622)) is a watermark-domain timer callback: it has the key, the timer's firing timestamp, and state handles — no envelope, no `seq` increment, no `ActivationContext`, no `ctx.memory.longterm`. Today it dead-letters a still-live suspension and then wipes all five state specs unconditionally ([dofn.py:660](../../../src/beam_agents/core/dofn.py:660)). The constitution's invariant 5 forbids external writes inside the pipeline with exactly one carve-out: "documented idempotent upserts to the long-term MemoryStore keyed by `(key, seq)`" — written for precisely this flush.

Adjacent constraints: compactors must never evict the LangGraph checkpoint namespace `__langgraph__/` ([checkpoint.py:26](../../../src/beam_agents/adapters/langgraph/checkpoint.py:26), [checkpoint.py:54](../../../src/beam_agents/adapters/langgraph/checkpoint.py:54)) — those keys are load-bearing resume state; and `Memory`'s public API today has no key enumeration at all, so no generic eviction strategy can currently be written against it. `add-longterm-memory-stores` (C29, sibling proposal in this batch) supplies the `MemoryStore` ABC and the configured long-term tier this change flushes to.

## Goals / Non-Goals

**Goals:**
- A safe default: an unconfigured pipeline survives hard-cap pressure by deterministic LRU eviction instead of dead-lettering forever.
- LLM summarization that is exactly as deterministic, atomic, and replay-cheap as the agent's own model calls — provable by the existing retry-determinism gate, not by prose.
- A demotion path at TTL: expiring working memory lands in the long-term tier effectively-once, and the wipe never outruns the flush.
- Zero proto and state-schema movement; strategies mutate state only through the existing facades.

**Non-Goals:**
- No prompt templating or summary-quality opinions in the runtime. The caller supplies the request builder and the response extractor; beam-agents is a runtime, not a framework (constitution, governing principle).
- No embedding/semantic compaction, relevance scoring, or retrieval — that is C29+ territory in the long-term tier.
- No mid-activation *asynchronous* compaction hook (i.e. no attempt to make `Memory._guarded_write` await). The sync hook's contract is untouched.
- No periodic/background summarization outside activations. Compaction happens where the effects can commit atomically or not at all.
- No change to the `ttl_expiry` conformance behavior when `on_expire` is unset.

## Decisions

### D1. Split the strategies by where they may run: the sync hook stays LLM-free; summarization is a driver-level step

The existing `Compactor` hook fires in the middle of a memory write, synchronously, on the event loop that any provider call would need — so an LLM-calling `compact()` is structurally impossible without blocking the loop (forbidden by the async-first rule and ruff's ASYNC lints) or spawning an out-of-band call (forbidden by D2). Rather than contorting the facade into an async write path — which would force `ctx.memory.set/append` to become awaitable and rewrite every agent — the change keeps two tiers with distinct contracts:

- **Tier 1 (emergency, in-write):** the existing sync `Compactor` hook, now actually populated by `DropOldestCompactor`. It must be cheap, deterministic, and LLM-free; it is the backstop that keeps a hard-cap-crossing write from failing the activation.
- **Tier 2 (scheduled, in-activation):** `SummarizeCompactor`, invoked by `run_activation` at a fixed lifecycle point — after `agent(ctx)` returns an outcome, before the outcome is folded into a `Continuation`/`ActivationResult` ([loop.py:217](../../../src/beam_agents/core/loop.py:217)) — and only when staged `memory.size_bytes` has reached its trigger threshold.

The two compose rather than compete: a key under sudden pressure is saved mid-write by tier 1, and the same activation's tier-2 pass then reduces bytes *semantically* so tier 1 stops being needed. An alternative — one polymorphic strategy object with both a sync and an async face — was rejected: the two tiers have different determinism obligations, different failure semantics (tier 1 failure propagates out of a memory write; tier 2 failure fails the activation wholesale), and different configuration (`AgentConfig.compactor` vs `AgentConfig.summarizer`), and gluing them into one interface hides exactly the distinction this change exists to make.

### D2. `SummarizeCompactor` runs inside the activation, through `ctx.call_model`, so its LLM calls are replay-cached — the centerpiece

The summarizer's model calls go through `ActivationContext.call_model` and nothing else. That single placement decision buys every property the runtime promises, for free, because it is the same path the agent's own calls take:

- **Replay-cached (invariant 3):** the call is keyed by content plus `(key, seq)`; the response is staged in the `ReplayCache` and committed with the bundle. When a bundle that already committed is replayed — or when the retry-determinism chaos wrapper forces re-processing — the summarizer's request hashes to the same key and is served from keyed state with zero provider calls. The summary bytes, and therefore the committed `MemoryBlob`, are byte-identical across replays.
- **Atomic (invariant 1):** the summary write (`memory.set`) and the cache insert stage in the same context as everything else. The summarizer runs inside `run_activation`'s existing failure wrap ([loop.py:207](../../../src/beam_agents/core/loop.py:207)): if it raises, `ActivationFailed` propagates, the DoFn commits nothing, and the key retains its pre-activation memory — a half-summarized blob can never commit.
- **Observable:** the call lands in the activation's trace as an ordinary `LLM_CALL` event and in the tally as `llm_calls`/`llm_ms`/`tokens`, with no new observability plumbing.

Rejected alternatives, each of which loses at least one invariant:

- *A separate summarization transform or service*: the LLM call happens outside keyed state, the summary re-enters as an element, and nothing ties its content to `(key, seq)` — retries produce divergent summaries and the atomic-commit story fragments across two transforms.
- *Summarizing from the TTL/HITL timer callbacks*: no activation context exists there (see D4), so the call would need a raw provider client with no cache, no staging, and wall-clock-dependent behavior in a callback that bundle retries re-run.
- *Calling the provider directly from inside the sync `compact()` hook*: impossible without blocking the bridge loop (D1), and even via loop-jumping hacks the call would bypass the cache and the staged effects.

Two placement details are load-bearing. First, the **trigger predicate is deterministic**: "staged `memory.size_bytes >= trigger_bytes` after the agent returns" is a pure function of committed state plus the activation's deterministic walk — no clock, no sampling — so a replayed bundle makes the identical run/don't-run decision. Second, the summarizer runs **before** the suspend path builds its `Continuation`, so `ctx.build_continuation` records a `step_index` that already includes the summarizer's `call_model` cursor advances ([context.py:686](../../../src/beam_agents/core/context.py:686)); a resume seeds from that cursor and can never re-mint an intent ID across the summarization. The summarizer itself stages no intents and no outputs — it holds a narrow structural view of the context (memory + `call_model`), not the full surface, so it *cannot* call `act`.

### D3. `DropOldestCompactor` is the wired default, which requires giving `Memory` an enumeration surface

Today an unconfigured pipeline turns memory pressure into permanent failure: the compactor parameter is dead ([dofn.py:483](../../../src/beam_agents/core/dofn.py:483)), so the hard cap's only behavior is `MemoryOverflow` → dead letter, forever, on every subsequent over-cap write. The default flips to `DropOldestCompactor` on a new `AgentConfig.compactor` field, threaded `RunAgent → _AgentDoFn → run_activation → ActivationContext → Memory` — the same route `tool_registry` took in `add-runtime-metrics`. "Oldest" means least-recently-used *entry*, the order the facade already maintains and persists (blob entries are emitted LRU-first); rings already self-bound per key via `max_items` ([facade.py:165](../../../src/beam_agents/memory/facade.py:165)), so entry-level LRU eviction is the correct granularity for the generic default.

Three consequences:

- **The facade needs `keys()` and `entry_size()`.** `Memory`'s public API has no enumeration, and the accessors it does have are LRU-*stamping*: a compactor that called `get()` to inspect candidates would move each inspected entry to most-recently-used, destroying the very order it is iterating. The new surface is therefore explicitly read-only with respect to access order — no `_touch`, no `dirty` — and returns keys least-recently-used first, matching `to_blob()`'s persisted order. This is an ADDED requirement on `memory-facade`; nothing existing changes.
- **Protected prefixes are part of the contract, not a convention.** The LangGraph checkpoint stores load-bearing resume state under `__langgraph__/` and already documents that compactors must not evict it ([checkpoint.py:26](../../../src/beam_agents/adapters/langgraph/checkpoint.py:26)). The default compactor enforces this structurally: `protected_prefixes` defaults to `("__langgraph__/",)` and matching keys are skipped during eviction. If only protected keys remain and the target is still exceeded, the compactor stops — and the facade's existing contract takes over (the write raises `MemoryOverflow`), which is the correct outcome: silently evicting resume state to admit a write would corrupt a suspended agent.
- **The target has hysteresis.** Eviction runs to `target_bytes`, default `HARD_CAP_BYTES // 2` (524 288) — below the 786 432-byte soft cap — so one compaction pass buys real headroom instead of leaving the facade oscillating at the soft-cap boundary where every write re-triggers the (once-per-instance) warning path and tier-2 summarization gets no room to work.

Determinism is trivial by construction: `compact()` reads only the staged entries and its own frozen configuration — no clock, no RNG, no I/O — so a replayed activation evicts the identical set. The behavior change (over-cap writes now succeed by eviction where they used to dead-letter) is called out in the proposal and Migration Plan with an explicit opt-out (`compactor=None`).

### D4. `on_expire` flushes at TTL fire, directly from `on_ttl`, under the invariant-5 carve-out — because no activation can exist there

The flush belongs at the moment of expiry, and the moment of expiry is a watermark timer with no activation context: no envelope, no new `seq`, no `ActivationContext`, and therefore no `ctx.memory.longterm` staging surface and no intent path scoped to an activation. This tension admits three designs:

- **(a) Flush directly in `on_ttl` — chosen.** Before the wipe, the callback reads `MEMORY` and the committed `SEQ`, and — when `on_expire` is configured alongside C29's long-term store — performs one idempotent upsert keyed by `(entity_key, seq)` through the store, submitted to the async bridge (which `setup()` already runs for the DoFn's lifetime) and bounded by a timeout. This is exactly the side effect invariant 5 carves out, in the words the constitution uses. Determinism: the upsert's content is a pure function of committed state plus the timer's firing timestamp (`expired_at_ms`), both replay-stable, so a retried timer bundle produces a byte-identical upsert that the `(key, seq)` key dedups to nothing.
- **(b) Route the flush through the last activation — rejected as the expiry mechanism, acknowledged as the eager alternative.** "The last activation before expiry" is unknowable at commit time — every commit re-arms the TTL timer precisely because it might *not* be the last. The only coherent version of this option is write-through mirroring: every committed activation also upserts its blob to the long-term tier. That taxes every activation's latency budget with a store write to cover the rare expiry case, and duplicates what C29's `ctx.memory.longterm` already gives agents that want eager persistence. It remains available to users — it is just not this hook.
- **(c) Flush as a `ToolIntent` through the effector — rejected.** Superficially attractive (side effects via intents, effector dedup), but: the intent payload would carry up to 1 MiB of `MemoryBlob` onto the intents topic; intent IDs are minted from `(key, seq, step_index)` inside activations and the admission/continuation machinery has no notion of a timer-minted flush; and the effector would need long-term-store credentials, expanding its trust surface — all to reimplement, with more moving parts, the dedup the `(key, seq)` upsert carve-out already provides.

**Failure semantics: flush-then-wipe, fail-closed.** The wipe runs only after the flush succeeds. On flush failure the callback raises, failing the timer bundle so the runner retries it; the idempotent upsert makes the retry safe, and the state — still un-wiped — is exactly what the retry needs. The alternative (wipe anyway, log the loss) silently defeats the hook's purpose; the alternative (swallow and leave state, don't re-fire) leaks state forever. The real risk is a wedged key during a long store outage — mitigated by the store adapter's own bounded retries/timeouts (C29's contract) and accepted deliberately: a user who configures `on_expire` is declaring that this memory must not be lost. With `on_expire` unset (the default), `on_ttl` is byte-for-byte today's behavior, and the `ttl_expiry` conformance scenario passes unchanged. The existing `ttl_wiped_suspension` dead-letter is emitted exactly as today; the flush additionally preserves the wiped key's memory, which is strictly more information for the post-mortem.

### D5. The runtime owns summarization lifecycle and determinism; the caller owns the prompt

`SummarizeCompactor` is configured with two callables: `build_request(items, prior_summary) -> LlmRequest` and `extract_summary(response_bytes) -> bytes`. The runtime decides *when* to summarize (deterministic trigger), *what* to feed (the oldest ring items beyond `keep_recent`, plus any existing summary scalar), *where* the call runs (D2), and *how* the result lands (replace folded items, write the summary scalar) — and it decides nothing about prompt text, model choice, or output parsing. This is the constitution's runtime-not-framework line applied literally: shipping a default summarization prompt would be prompt templating, the named example of what must be rejected. It also matches the established pattern for provider-shaped concerns — `AgentConfig.decode` is already a caller-supplied callable for exactly this reason, and `LlmRequest`/response bytes are opaque provider-shaped material everywhere in the model layer ([client.py:21](../../../src/beam_agents/model/client.py:21)).

The one determinism obligation this transfers to the caller — `build_request` must be a pure function of its inputs — is stated as a spec requirement, and its violation is *detected*, not silently absorbed: an impure builder produces a different cache key on replay, misses the cache, and the retry-determinism gate's zero-extra-calls assertion fails.

## Risks / Trade-offs

- **Default-behavior change** → over-cap writes that used to dead-letter now succeed via eviction, and an agent may observe previously-written keys as absent. Mitigation: called out in the proposal and Migration Plan; `compactor=None` restores the old contract; protected prefixes keep resume state exempt; eviction is visible in the memory facade's existing soft-cap warning and in `memory_bytes` samples.
- **Drop-oldest can evict semantically important entries** → LRU is a heuristic, not a relevance judgment. Mitigation: protected prefixes for structurally critical keys; `SummarizeCompactor` exists precisely to preserve meaning under pressure; agents can pin what matters by re-touching it (reads update LRU by design).
- **Summarization adds provider latency and cost at threshold crossings** → an activation that crosses the trigger pays one extra model call. Mitigation: the deterministic trigger with `keep_recent` and the tier-1 hysteresis target make crossings rare; the call is fully visible in `llm_calls`/`llm_ms`/`tokens` and traces; the replay cache makes retries free.
- **A summary response larger than the cache's 100 KiB blob cap degrades to digest-only** → a digest-only entry replays no bytes, so a bundle retry would re-call the provider ([replay_cache.py:178](../../../src/beam_agents/model/replay_cache.py:178)); the digest comparison detects divergence but cannot prevent the extra call. Mitigation: summaries are by construction small (they exist to shrink bytes); the spec requires the summarizer to reject an extracted summary larger than the item bytes it replaces, so a pathological "summary" cannot inflate memory either.
- **A wedged key during a long-term-store outage** → fail-closed flush retries the timer bundle until the store recovers. Mitigation: bounded per-attempt timeout via the bridge; C29's store adapters own bounded retries; accepted as the meaning of configuring `on_expire` (see D4). Flush failures are visible as failed timer bundles at the runner level; a dead letter cannot be used here, because a raising callback's bundle discards its outputs.
- **Impure user-supplied `build_request` breaks replay silently-ish** → mitigation: determinism stated as a requirement; violations surface as cache misses under the retry-determinism gate rather than as corrupted state (the blob is still whatever the committed attempt wrote).
- **`on_ttl` grows I/O and duration** → a state-heavy callback where there was none. Mitigation: flush only when configured and memory is non-empty; single upsert per expiry; timer callbacks already tolerate bounded work (`on_hitl` mints intents today).

## Migration Plan

1. Land the `memory-facade` enumeration surface and `DropOldestCompactor` with wiring (`AgentConfig.compactor` default). This is the behavior-changing step: release notes state that hard-cap overflow now evicts LRU entries by default and that `compactor=None` restores strict-overflow semantics. No state, wire, or `--update` implication — nothing about the blobs changes shape.
2. Land `SummarizeCompactor` and the loop-driver invocation point (`AgentConfig.summarizer`, default `None` — purely opt-in, no behavior change when unset).
3. After C29 merges, land `on_expire` (`AgentConfig.on_expire`, default `None` — opt-in; `on_ttl` unchanged when unset).
4. Rollback at any step is a code revert with no data implications; keyed state written under the new defaults is ordinary `MemoryBlob` content readable by older code.

## Open Questions

- Should `DropOldestCompactor` support ring-item-level trimming (drop oldest items within a ring before dropping whole entries)? Deferred: rings are already per-call bounded, and entry-level LRU is predictable; item-level policies can ship as additional strategies without touching the protocol.
- Should the summarizer's trigger also count activations-since-last-summary (time/turn-based folding) rather than bytes only? Bytes is the deterministic, state-derivable signal today; a turn counter would need a home in `MemoryBlob` and is deliberately out of scope.
- Should `on_expire` flush the *summary only* (running a final summarization at expiry) instead of the raw blob? Rejected for now — no activation context at TTL fire means no replay-cached LLM call (D2/D4); revisit if C29 grows an out-of-band summarization tier.
- Should the effector's results topic carry a signal when a flushed key is later re-activated, so the agent can rehydrate from the long-term tier? That is C29's `ctx.memory.longterm` read path; noted here only as the consumer of what this flush writes.
