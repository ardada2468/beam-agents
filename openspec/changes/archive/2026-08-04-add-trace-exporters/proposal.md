## Why

`add-trace-events` made `.traces` carry a fully-correlated, deterministic trace stream — and gave it exactly one and a half exits. A `traces_to` URI resolves to raw serialized bytes on Kafka/Pub/Sub, or to `WriteToBigQuery` called with **no schema, no partitioning, and no create disposition**, so the BigQuery path only works against a hand-created table whose layout is documented nowhere and enforced by nothing. And the project's stated observability story — "OTLP exporter, BigQuery trace sink" (`project.md`, External dependencies) — is half missing: there is no OTLP path at all, so the trace stream cannot reach Jaeger, Tempo, Cloud Trace, or any OTel collector, despite the events already carrying W3C-width trace/span IDs and OTel GenAI attributes precisely so that they could.

The OTLP gap is the sharp one. A naive exporter DoFn that POSTs per element would put a network round-trip on the hot path of every trace event — hundreds per bundle — and a collector hiccup would fail bundles and stall the pipeline over *telemetry*. Trace delivery must cost near-zero on the processing path and must never make observability a source of unavailability.

## What Changes

- **New `otlp://` scheme for `AgentConfig.traces_to`.** `otlp://<host>:<port>` resolves to an OTLP/HTTP (protobuf) trace exporter targeting the collector's standard `/v1/traces` endpoint. Valid only for `traces_to`; `DefaultSinkResolver.validate` rejects it for `intents_to`/`errors_to` at config-construction time.
- **A batched, non-blocking OTLP export DoFn.** `process()` converts `TraceEvent`s to OTLP spans and appends to an in-memory batch — no I/O. Full batches are handed to a background sender thread through a bounded queue; `finish_bundle()` flushes the remainder and waits for the queue to drain up to a flush deadline. Export failures and queue overflow **drop and count, never raise**: a dead collector costs dropped telemetry, not a stalled pipeline. Delivery is best-effort at-least-once (the trace stream's deterministic IDs make collector-side dedup exact); the durable record remains the `.traces` PCollection itself.
- **Deterministic TraceEvent→OTLP mapping.** Trace/span/parent IDs pass through at their native 16/8-byte widths; `start_ms`/`end_ms` become unix nanos; attributes map to string key/values; `ERROR` events carry OTLP error status. `ACTIVATION_END` is exported as the activation span (it carries status and kind); `ACTIVATION_START` is not exported, because both events share one span ID and OTLP backends treat a span ID as unique.
- **Transport is `httpx` + `opentelemetry-proto`, not the OTel SDK.** The SDK's global tracer state and its own worker threads conflict with this repo's no-global-mutable-state rule and the Beam worker model; OTLP/HTTP export is one POST of one proto message, and `httpx` is already a core dependency. `opentelemetry-proto` ships as a new optional extra (`otlp`), imported lazily at `resolve()` time, so the core install and the offline unit lane stay clean.
- **An explicit BigQuery trace-table schema and a real writer.** A published `TableSchema` matching `trace_event_to_row` exactly, plus a new `event_time` TIMESTAMP column derived from `start_ms`. The `bigquery://` traces sink becomes a writer configured with that schema, `CREATE_IF_NEEDED`/`WRITE_APPEND`, day partitioning on `event_time`, and clustering on `trace_id` — so pointing `traces_to` at an empty dataset just works, and the table it creates is the one the queries in the capability's docs are written against.

## Impact

- **New code:** `observability/otlp.py` (TraceEvent→OTLP mapping, the batched sender, `WriteTracesToOtlp` transform). New `trace-exporters` spec.
- **Modified code:** `observability/exporters.py` (`event_time` on `trace_event_to_row`, `TRACE_TABLE_SCHEMA`, the schema'd BigQuery writer factory); `core/transform.py` (`DefaultSinkResolver`: `otlp` scheme parse/validate/resolve, `_WriteTraces` BigQuery arm uses the schema'd writer); `pyproject.toml` (optional extra `otlp = ["opentelemetry-proto"]`, mirrored into the `integration` group).
- **Dependencies:** `opentelemetry-proto` (pure generated protos, no SDK, no grpc) — optional extra only; lazy import keeps `import beam_agents` and the offline unit lane dependency-free. `httpx` (already core) is the transport.
- **No wire/state change:** `TraceEvent` is untouched; no `state_schema_version` implications; no new goldens.
- **Behavior change:** a `bigquery://` traces sink now creates and shapes its own table (previously: runtime failure unless a table with a guessed-at layout pre-existed). Rows gain `event_time`. Existing tables created by hand against the old row shape need the one added column.
- **Failure-mode contract:** OTLP export is explicitly lossy-under-failure (dropped-span and export-failure counts surface as Beam metrics, tallied on the Beam thread at `finish_bundle` since background-thread metric updates are silently discarded). Anyone needing lossless trace retention points `traces_to` at Kafka/Pub/Sub/BigQuery instead — stated in the spec, not discovered in an incident.
- **Tests:** all offline — mapping determinism and ID-width tests; batching/flush/drop-policy tests against an injected `httpx.MockTransport` (the same pattern the provider clients use); schema↔row agreement test (every row key present in the schema with the right type, and vice versa); resolver tests for the new scheme including its rejection on `intents_to`/`errors_to`; a TestPipeline run with a fake sender asserting no bundle failure under a failing collector.
- **Mutation gate:** the exporter itself lives under `observability/`, outside the `core/` gate, but `core/transform.py`'s resolver growth moved its ratcheted no-tests ceiling 242 → 371 (documented in `mutation-baseline.toml`): the new arms sit in the resolver territory only the mutmut-deselected `test_transform.py` reaches, the same pattern as `_WriteTraces` before them. A selected-file split for the new sink tests was tried and reverted — mutmut's per-function reach turned 92 kafka/pubsub-arm mutants into unkillable-without-IO-introspection survivors.
