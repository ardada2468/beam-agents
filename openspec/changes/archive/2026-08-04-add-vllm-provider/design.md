## Context

The provider seam is complete and has two real HTTP implementations. `LLMClient` is an async structural `Protocol` returning opaque `LlmResponse` bytes (`model/client.py`), the retryable/non-retryable error taxonomy drives `LlmFacade`'s retry and circuit-breaker decisions by exception type (`facade.py` `_call_with_retry` catches `ProviderError`; `ProviderRequestError` deliberately sits outside the base), and the facade is cache-first: a replay-cache hit returns before the breaker or provider is ever consulted, which is the entire bundle-retry determinism argument. Providers are constructed by `_AgentDoFn.setup` through `AgentConfig.provider_factory` and dropped in `teardown`; each DoFn instance runs one `AsyncBridge` thread with a dedicated asyncio loop, and `OpenAICompatProvider` already covers a vLLM OpenAI server by base URL alone (C12 design, "the OpenAI-compatible client already covers vLLM's OpenAI server by base URL").

What is missing is (a) a vLLM-shaped preset of that client — required base URL, optional auth — and (b) the GPU-worker sidecar `project.md` sanctions: an in-process engine held as a worker-local singleton via `beam.utils.shared.Shared` (the one documented exception, alongside circuit breakers, to the no-global-mutable-state rule). The load-bearing Beam facts: a worker process hosts many DoFn instances (threads), each with its own bridge loop; `Shared` stores the constructed object per-process keyed by the `Shared` handle's identity and holds it by **weak reference** — acquirers keep it alive with strong references; a pickled `Shared` handle deserializes to the same identity in every DoFn instance, which is precisely the sharing mechanism.

## Goals / Non-Goals

**Goals:**
- Two drop-in `LLMClient`s in `model/vllm.py` usable via `provider_factory` with zero changes to `core/dofn.py`, `core/loop.py`, or `model/facade.py`.
- Exactly one engine (one copy of model weights) per worker process regardless of DoFn instance count, via `apache_beam.utils.shared.Shared`.
- Fail-fast health semantics: an engine that cannot load or answer a bounded readiness probe fails the worker in `setup`, before any element.
- Graceful engine shutdown when the last holder releases it — never while a sibling DoFn instance still shares it.
- Sidecar responses that are cacheable opaque bytes decodable by the existing OpenAI-compatible `Decode`, preserving the replay-cache contract and zero-extra-calls bundle retries.
- Default test tier stays GPU-free, `vllm`-free, and offline via an injectable engine seam; the `vllm` extra follows the established optional-dependency pattern.

**Non-Goals:**
- Streaming / token-incremental delivery (same v0 exclusion as C12; the cache and `LlmResponse` assume a whole payload).
- Owning vLLM deployment: container images, CUDA/driver provisioning, Dataflow GPU pool configuration, tensor-parallel topology tuning — documented, not automated.
- A Vertex provider, embeddings, or any non-chat completion surface.
- Retry/backoff/circuit policy — owned by `LlmFacade`; the sidecar only classifies failures by type.
- Making the sidecar the default anywhere; `FakeLLM` remains the test default and no `AgentConfig` default changes.

## Decisions

### D1. Endpoint mode is a preset that delegates to `OpenAICompatProvider`, not a fork

`VllmEndpointProvider` wraps a contained `OpenAICompatProvider` and differs in exactly two knobs: `base_url` is a required constructor argument (no `api.openai.com` default to mis-hit), and `api_key` is optional — when absent, no `Authorization` header is sent, matching unauthenticated vLLM deployments. Request shape, raw-bytes passthrough, `stream: false`, the `_http.py` taxonomy mapper, and the `Decode` are all inherited by delegation. **Why:** the C12 spec already promises base-URL portability to vLLM servers; duplicating the HTTP path would fork the spec-verified taxonomy mapping and invite drift. The only genuinely new behavior (header omission) lives in the preset. **Alternative rejected:** documentation-only ("just use `OpenAICompatProvider` with a dummy key") — leaves the required-key/wrong-default hazard in place and gives the sidecar no endpoint sibling to mirror in `model/vllm.py`.

### D2. One engine per worker process via a pipeline-construction-time `Shared` handle

`vllm_sidecar_factory(engine_config, ...)` constructs a `Shared()` handle **once, at pipeline-construction time**, and returns a `provider_factory` closure that captures it. Every DoFn instance deserialized in a worker process carries the same handle identity, so `shared.acquire(constructor_fn, tag)` resolves to one engine; the tag is a digest of the engine configuration, so a config change on pipeline update re-acquires a fresh engine instead of silently reusing a stale one. **Why:** `Shared`'s per-process map is keyed by handle identity — a `Shared()` created *inside* the factory body would mint a new identity per DoFn instance and defeat sharing entirely, loading weights per instance (the OOM trap this design exists to prevent). This is also the exact singleton shape `project.md:88` documents. **Alternative rejected:** a module-level global engine dict keyed by config — reimplements `Shared` badly (no weakref lifecycle, no tag semantics) and violates the "documented worker-local singletons only" rule's letter.

### D3. The shared engine handle owns a dedicated engine thread and event loop

The `Shared` constructor builds an engine handle that starts one background thread running its own asyncio loop, imports `vllm` lazily, and instantiates the async engine on that loop. `VllmSidecarProvider.complete` — a coroutine running on the DoFn's bridge loop — submits generation to the engine loop with `asyncio.run_coroutine_threadsafe` and awaits the result via `asyncio.wrap_future`, so the bridge loop never blocks and the async-only `LLMClient` protocol is preserved. **Why:** asyncio objects are loop-bound and there are N bridge loops (one per DoFn instance, per the stateful-runtime spec) but must be exactly one engine; parking the engine on any one bridge loop couples its lifetime to one DoFn instance and makes every other instance's access a cross-loop violation. A loop the engine handle owns is the only topology where "one engine, N clients" is safe. **Alternative rejected:** vLLM's synchronous `LLM` entrypoint called via `run_in_executor` — serializes callers behind an executor and forfeits vLLM's continuous batching across concurrent requests, which is the sidecar's throughput argument.

### D4. Health check at construction time, inside `setup`, through the existing factory seam — no `core/` change

`_AgentDoFn.setup` already calls `provider_factory()` after starting the bridge (dofn.py:248-251). `VllmSidecarProvider.__init__` acquires the shared engine and runs a bounded readiness probe — submit a trivial engine round-trip (model metadata / health coroutine) to the engine loop and block on `Future.result(timeout=health_deadline_s)`; failure or deadline raises out of the constructor, hence out of `setup`. **Why:** raising from `setup` is Beam's fail-fast path — the runner retries/replaces the worker before it takes elements, instead of dead-lettering every element against a wedged engine one activation at a time. Doing it in the constructor needs no DoFn hook: the factory *is* the setup-time seam, and blocking briefly is safe there because `setup` runs on the Beam worker thread, not the bridge loop. The probe deadline is a constructor knob because weight loading legitimately takes minutes on large models. **Alternative rejected:** generic `check_health()`/`aclose()` lifecycle hooks on `_AgentDoFn` — touches `core/` (mutation gate, wider blast radius) and gets teardown semantics wrong: a per-DoFn `aclose` would shut an engine sibling instances still share. Release-not-close (D5) is the correct per-instance operation, and `teardown` already performs it.

### D5. Graceful teardown by last-reference release, enforced by `Shared`'s weakref contract

`Shared` holds the engine handle weakly; each provider holds it strongly for the DoFn's lifetime. `teardown` already nulls the provider (dofn.py:253-257), dropping that strong reference. The engine handle registers a `weakref.finalize` that stops the engine loop, joins the engine thread, and releases the engine (freeing GPU memory) — so shutdown runs exactly when the last DoFn instance in the process lets go, and an engine still held by a sibling instance survives any other instance's teardown untouched. **Why:** this is the only ordering that is correct for a shared resource with independent per-instance lifecycles, and it costs zero `core/` changes; CPython refcounting makes the release prompt in the common case. On hard worker death no finalizer runs, which is fine — the process's GPU allocation dies with it. **Alternative rejected:** explicit reference counting inside the handle — hand-rolls what `Shared`'s weakref semantics already provide and adds a decrement path every future provider must remember to call.

### D6. Sidecar output is serialized as canonical chat-completions-shaped bytes

The sidecar builds a minimal chat-completions-shaped JSON body from the engine output — `choices[0].message.content` and a `usage` object with `prompt_tokens`/`completion_tokens`/`total_tokens` from the engine's token accounting — serialized canonically (sorted keys, compact separators, UTF-8) and returned as `LlmResponse` bytes. `AgentConfig.decode` for both vLLM modes is the existing `openai_compat.decode`. **Why:** the opaque-bytes contract makes the response body the cache payload; giving the sidecar the same shape as endpoint mode means one `Decode` serves both, switching modes never changes decode wiring, and the facade's usage/trace path works unchanged. Canonical serialization keeps digests stable for golden tests. Replay determinism does not depend on this — the replay cache guarantees a retried bundle re-reads the stored bytes and makes zero engine calls — but stable serialization removes a class of digest-flake in tests. **Alternative rejected:** a sidecar-native response shape plus a third `Decode` — a second decode contract to maintain for zero benefit.

### D7. Engine access goes through a narrow internal seam; `vllm` imports stay inside the constructor

The handle drives the engine through a small internal protocol (async generate over the request material → output text + token counts, plus a readiness coroutine). The real implementation imports `vllm` lazily inside the `Shared` constructor function; unit tests inject a fake engine implementing the seam (scripted outputs, scripted failures, scripted delays) via a test-only constructor parameter. **Why:** CI has no GPU and must not install multi-GB CUDA wheels; every sidecar behavior in the spec — singleton acquisition, health probe, taxonomy mapping, byte shape, last-holder shutdown — is observable at the seam and therefore offline-testable, mirroring how C12 verified taxonomy mapping with `httpx.MockTransport` instead of live endpoints. It also keeps `import beam_agents.model` working without the extra (the established `effector`/`langgraph`/`otlp` lazy-import rule). Real-engine coverage is one `smoke`-marked test that skips without the extra and a visible GPU. **Trade-off accepted:** the seam is a simplification of vLLM's real API surface; the pinned version floor plus the smoke test bound the drift.

### D8. Engine failures reuse the existing taxonomy with conventional statuses, not new error types

Mapping: engine/scheduler saturation (queue full, KV-cache exhaustion admission failure) → `RateLimitError(retry_after_ms=None)`; engine internal failure (generation raised, engine dead/errored) → `ServerError(status=500)`; per-request generation deadline exceeded → `ProviderTimeout`; request material the engine rejects as invalid (bad sampling params, prompt over the model's max length) → `ProviderRequestError(status=400)`. **Why:** the facade classifies strictly by the existing types (`_call_with_retry` catches `ProviderError`; everything else propagates), so reusing them means the sidecar composes with retry/breaker/trace with zero facade changes; backpressure-as-`RateLimitError` gives exactly the backoff behavior an overloaded local engine needs. The `500`/`400` statuses are conventional stand-ins — the taxonomy's constructors require a status and in-process failures have none — and are documented as such on the mapping. **Alternative rejected:** new engine-specific error classes — the facade would need to learn them, splitting the "classification is by existing type, never string-matching" invariant for no added signal.

## Risks / Trade-offs

- **No GPU anywhere in CI** → every spec scenario is exercised offline at the engine seam (D7); the single real-engine test is `smoke`-marked and skip-gated on the extra plus GPU visibility, so nightly stays green on GPU-less runners. Residual risk of seam/reality drift is bounded by the `vllm` version floor and surfaces in smoke, not in user pipelines first.
- **Weight loading can exceed runner setup patience** → the health-probe deadline is a constructor knob with a generous default; the docstring documents that large models need a raised deadline and pre-baked container images. A deadline overrun fails `setup` loudly (D4) rather than hanging a bundle.
- **`vllm` in the universal lockfile** → the extra's dependency tree (torch/CUDA) is heavy and platform-constrained; if `uv lock`'s universal resolution chokes, constrain the extra with environment markers rather than loosening the project's Python/platform floor. Flagged as an open question; the extra is never installed in any CI lane either way.
- **Finalizer-based shutdown is best-effort under hard kill** → accepted: SIGKILL forfeits any graceful path and the OS reclaims the GPU with the process. The semantics gates already treat hard-killed workers as a first-class scenario, and correctness never depends on engine shutdown (effects are staged/committed via Beam, not via the engine).
- **A momentary zero-holder window could evict the engine** (Shared holds it weakly) → providers hold the strong reference for the whole DoFn lifetime, and the only release site is `teardown`; a worker that tears down every instance is exiting anyway. A unit test pins "engine survives one-of-two release, dies at last release".
- **Sidecar shares the worker's memory/CPU with the runtime** → inherent to sidecar mode; the latency budget (runtime overhead excluding LLM time) is unaffected by design since engine time is model time, but the docs must tell operators to size GPU workers for weights + KV cache + the pipeline's own footprint.
- **Nondeterministic sampling on a local engine** → identical to remote providers: determinism under bundle retry comes from the replay cache's zero-extra-calls guarantee, not from the engine; the existing retry-determinism gate covers the composed behavior with `FakeLLM`, and the fake-engine tests assert the cached path never reaches the engine.

## Migration Plan

Additive only. New module `src/beam_agents/model/vllm.py`, new re-exports from `beam_agents/model/__init__.py`, one new `pyproject.toml` extra, new tests. No existing type, signature, proto, or state changes shape; no call site migrates; `state_schema_version` is untouched. Rollout is "land and it's available via `provider_factory`" — endpoint mode immediately, sidecar mode wherever the `vllm` extra and a GPU exist. Rollback is deleting the module, the re-exports, and the extra. Existing users pointing `OpenAICompatProvider` at vLLM keep working unchanged; migrating to the preset is optional ergonomics.

## Open Questions

- Should `vllm_sidecar_factory` expose a pass-through for arbitrary vLLM engine args (tensor parallel size, dtype, quantization, GPU memory fraction) as an opaque mapping folded into the `Shared` tag, or a typed subset only? (Leaning opaque mapping + digest into the tag: vLLM's engine-arg surface churns faster than we should chase.)
- Does `uv lock`'s universal resolution accept the `vllm` extra as-is, or does it need environment markers (platform/accelerator) to keep the lockfile portable? Resolved at implementation time; the fallback is markers, never weakening the core dependency set.
- Should the sidecar populate a deterministic sampling seed from `(key, seq)` when the caller supplies none, making cold-cache re-runs more reproducible? (Leaning no for v0: replay determinism is already owned by the cache, and a synthetic seed silently changes model behavior.)
- Is one smoke test (load small model, one `complete`, decodable non-empty response) enough for the first cut, or should smoke also cover concurrent submissions from two bridge loops? (Leaning add the concurrency case only if the seam tests prove insufficient.)
