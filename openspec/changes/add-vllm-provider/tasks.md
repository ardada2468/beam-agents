## Revisions

### Revision 1 — the lifecycle tests must displace Beam's `Shared` keepalive

Design D5 says the engine dies "exactly when the last DoFn instance in the process lets go", resting on `Shared` holding the singleton weakly. Reading the installed `apache_beam/utils/shared.py` during implementation surfaced one more strong reference the design did not account for: `_SharedMap` keeps a process-global `self._keepalive = (key, result)` pointing at the **most recently acquired** object, precisely so a momentary zero-holder gap between work items does not evict an expensive model. It is displaced as soon as any *other* `Shared` handle is acquired.

Nothing in D5's argument changes — the finalizer still runs on last release, and in a real worker the keepalive is displaced by ordinary pipeline activity (at worst, reclamation is delayed to a point where the process is exiting anyway). But a unit test that releases both providers and calls `gc.collect()` would observe the engine still alive, so the two lifecycle tests call a `_displace_shared_keepalive()` helper (acquiring a throwaway `Shared`) before collecting. This is a test-harness fact, not a behavior change: no source or spec text needed amending. It also strengthens one entry in design.md's risk list — the "momentary zero-holder window could evict the engine" risk is in fact mitigated by this keepalive, not merely accepted.

### Revision 2 — the lockfile is not regenerated here

Task 5.1 said "regenerate the lockfile". The `vllm` extra is declared in `pyproject.toml` as proposed, but `uv.lock` is deliberately left byte-identical in this worktree: resolving vLLM's torch/CUDA tree is exactly the universal-resolution question design.md flagged as open, it cannot be validated on a GPU-less container, and no CI lane installs the extra (`uv sync --locked --group lint --group typecheck --group test` never sees it). The lock refresh — and the environment markers it may require, per the design's stated fallback — belongs with the first environment that can actually resolve and exercise the extra, alongside the blocked real-engine smoke run in 6.1. Nothing in this change's offline behavior depends on it: the extra is consulted only by the lazy import inside `_RealVllmEngine`.
