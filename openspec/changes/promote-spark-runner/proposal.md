## Why

Runner portability is a named differentiator ([project.md:7](../../project.md), [project.md:9](../../project.md)), yet the v1.0 support statement draws the line at [project.md:113](../../project.md): "Supported runners v1.0: DirectRunner, Dataflow, Flink. Spark is best-effort." Today "best-effort" means *unexercised*: the conformance matrix runs on exactly two legs — `LEGS = (DIRECT, FLINK)` at [_spec.py:34](../../../tests/conformance/_spec.py:34) — and nothing in the repository ever submits a pipeline to a Spark runner. Whether the runtime works on Spark reduces to whether the Spark portable runner correctly executes the primitives `core/dofn.py` stands on — `ReadModifyWriteStateSpec`/`BagStateSpec`/`CombiningValueStateSpec` keyed state plus `WATERMARK` and `REAL_TIME` timers under streaming checkpointing ([project.md:52](../../project.md)–53) — and that is exactly what the matrix's Flink leg already proves per adapter and per scenario over Kafka-shaped ingress/egress ([_flink/harness.py:336](../../../tests/conformance/_flink/harness.py:336), [_flink/pipeline.py:146](../../../tests/conformance/_flink/pipeline.py:146)).

A promotion from best-effort to supported must be *earned by evidence*, not asserted by an edit to `project.md`. This change defines the promotion process in two stages: first a `spark` conformance leg with a weekly (not per-PR) CI workflow, then a mechanical gate — four consecutive weeks of green scheduled runs with zero skips added — that authorizes flipping the support statement, plus the symmetric demotion path. The change deliberately does not claim Spark works today: the leg's initial Run/Skip declarations are findings (the Spark portable runner's streaming state/timer support is an open question, see `design.md`), and if the leg stays red or mostly-skipped, the status stays best-effort with the evidence public.

## What Changes

**Stage 1 — the spark conformance leg (implemented by this change):**

- Extend the leg vocabulary: `LEGS` grows from `("direct", "flink")` to `("direct", "flink", "spark")` at [_spec.py:34](../../../tests/conformance/_spec.py:34). Every one of the seven scenarios declares the spark leg per-scenario through the existing `Run`/`Skip(reason)` vocabulary ([_spec.py:42](../../../tests/conformance/_spec.py:42)–58, [_spec.py:141](../../../tests/conformance/_spec.py:141)); some scenarios are expected to start as `Skip` with documented reasons (e.g. portable-runner timer/state feature gaps, or the in-process-chaos constraint that already skips `bundle_retry_cache` on Flink at [_spec.py:277](../../../tests/conformance/_spec.py:277)). The meta-test's expected-cell accounting extends mechanically because [test_matrix.py:21](../../../tests/conformance/test_matrix.py:21)–27 iterates `LEGS`.
- New `tests/conformance/_spark/{harness,pipeline}.py`, parallel to `tests/conformance/_flink/`: one multiplexed portable-runner job per adapter reusing the existing merged provider/registry/dispatch-agent machinery and the responder/drainer/topic-watcher harness pieces, submitting to a Beam **Spark job server** instead of the Flink one, with the same `InfraFailure` separation ([_flink_stack.py:46](../../../tests/semantics/_flink_stack.py:46)) so stack problems never read as runner verdicts.
- New compose overlay `docker/compose.spark.yaml` (Spark job server image pinned by digest, embedded local master initially, shared artifact-staging volume, and a spark-scoped SDK-harness worker-pool service mirroring the namespace-binding pattern documented at [compose.yaml:152](../../../docker/compose.yaml:152)–171). The base [compose.yaml](../../../docker/compose.yaml) is untouched so per-PR `integration` jobs pay nothing for Spark.
- New weekly workflow `.github/workflows/spark-weekly.yml`: `schedule` (weekly cron) + `workflow_dispatch`, bringing up the base stack plus the spark overlay and running `make test-conformance-spark`. It is **not** triggered by pull requests and is **not** a required check. A new `spark` pytest marker joins the closed registry ([pyproject.toml:396](../../../pyproject.toml:396)); spark-leg cells carry `integration + spark` (not `semantics` while best-effort — see design D4), and the per-PR selections (`test-integration`, `test-semantics`, `test-conformance-flink` at [Makefile:54](../../../Makefile:54)) are adjusted to exclude them.
- Mechanical promotion-window tracking: a `scripts/spark_weekly_status.py` step in the weekly workflow queries the last scheduled-run conclusions of `spark-weekly.yml` via the GitHub API, computes the current consecutive-green streak (scheduled runs only, with weekly-cadence gap detection), scans the 28-day window for added spark `Skip` declarations, and writes the streak and promotion-readiness verdict to the job summary. The script *reports*; it cannot flip status (see design D5 for the honest limits).

**Stage 2 — the promotion gate and demotion path (process defined by this change, executed as follow-up changes):**

- **Promotion:** after **4 consecutive green scheduled weekly runs with zero spark `Skip` declarations added** during the window, a follow-up OpenSpec change flips Spark's status from best-effort to supported: update the support statement at [project.md:113](../../project.md), the README, and `docs/ci.md`, and mark the weekly spark leg **required** — a red weekly run becomes a release blocker — while remaining weekly, still not per-PR.
- **Demotion:** after promotion, **two consecutive red scheduled weekly runs** trigger a demotion change: status returns to best-effort, announced in the README and release notes; the weekly leg keeps running so re-promotion uses the same 4-week gate.

## Capabilities

### New Capabilities

- `spark-runner-support`: the Spark portable-runner promotion process — the spark conformance leg and its per-scenario Run/Skip declarations, the weekly (never per-PR) workflow, the mechanical promotion-window reporting, the 4-consecutive-green-weeks promotion gate, and the two-red-weeks demotion path.

### Modified Capabilities

- `adapter-conformance-matrix`: the runner-leg set gains the weekly spark leg (the two-runner requirement becomes three-legged with per-leg cadence), and the marker/accounting clause is updated so spark cells carry `integration + spark` instead of `semantics` while best-effort, without disturbing the semantics-partition guarantees of the direct and flink legs. Delta applies on top of the pending `add-adapter-conformance-matrix` change (see design D8 for archive sequencing).
