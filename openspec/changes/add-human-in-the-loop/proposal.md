## Why

Correctness invariant 6 says timeouts fail closed at both layers — the HITL timer fires the fallback path *and* the effector refuses expired intents — but neither layer is actually built. Today an agent has no way to *request* an approval (`AgentEnvelope.Approval` can arrive, but nothing mints the intent it answers), the HITL timer emits a hard-coded `b"__hitl_timeout__"` sentinel with no configurable routing, `expires_at_ms` is stamped on intents and then never read by anybody, and a resume is admitted purely on `intent_id` membership with no deadline check at all. The result is a system that *looks* fail-closed and is in fact fail-open: an approval that arrives an hour after its deadline resumes the agent and executes the side effect it was supposed to block.

## What Changes

- **Approval intents.** Add `request_approval(...)` to both context surfaces (`AgentContext`, `ActivationContext`). It stages a `ToolIntent` carrying the new `kind = APPROVAL` discriminator, a canonical-JSON payload describing what is being approved, and a mandatory `expires_at_ms`. `intent_id` determinism is unchanged (`uuid5` over `(entity_key, seq, step_index)`), so a replayed activation re-mints byte-identical approval requests.
- **`HitlPolicy` fallback routing.** Add `beam_agents/hitl.py` with a frozen `HitlPolicy` (default timeout, default intent TTL, approval channel name, escalation bound) and three routes the policy may return for a timed-out continuation: `Deny` (deterministic bytes on `.output`), `Drop` (a typed `hitl_timeout` record on `.errors`, nothing on `.output`), and `Escalate` (a deterministic escalation intent on `.intents` plus a re-armed deadline, bounded by `max_escalations`). The policy is a **pure function** — no model calls, no bridge, no `SEQ` increment — because timer callbacks re-execute on bundle retry. Wire it through `AgentConfig(hitl_policy=...)`.
- **Timer fires with `kind="timer"` and the expired handle.** `HITL_TIMER`'s callback takes the timer's fire timestamp (`beam.DoFn.TimestampParam`), reads the live `Continuation`, and invokes the policy with a `FallbackContext(kind="timer", ...)` carrying the *expired* continuation handle (seq, snapshot, deadline, pending intent IDs, fire time). A fire whose timestamp predates the live continuation's `deadline_ms` is a **stale handle** — superseded by a later suspension — and is a no-op that mutates nothing.
- **`expires_at` fail-closed at both layers.** Layer 1: `_resume` admits a result/approval only when the continuation is live *and* `now_ms < deadline_ms` *and* `now_ms < expires_at_ms` of the matching pending intent; anything else is `orphaned_result` on `.errors` with zero state mutation. Layer 2: `hitl.py` exports the pure effector-side guard (`intent_expired` / `refuse_expired` → `ToolResult(status=EXPIRED)`) that a reference effector calls before executing anything. The suspend deadline becomes `min(suspend timeout, earliest staged intent expiry)` so the two layers can never disagree about who is still live.
- **`AgentContext.act` stamps `expires_at_ms`.** It currently leaves it `0`, which under fail-closed semantics would mean "already expired". It now takes the TTL from `HitlPolicy.intent_ttl_ms`, matching `ActivationContext.act`.
- **Resumed activations continue their step index.** A resumed activation currently restarts `step_index` at `0` within the same `seq`, so its first `act(...)`/`request_approval(...)` re-mints an `intent_id` the suspended activation already used and the effector dedups the new effect away as a duplicate. The resumed context is now seeded from `Continuation.step_index`, and escalation intents extend from there. This is a prerequisite for approvals that are requested on resume.
- **Proto (additive only, no `state_schema_version` bump).** `ToolIntent.kind` (enum: `TOOL_KIND_UNSPECIFIED`/`TOOL`/`APPROVAL`) and `Continuation.escalations` (uint32).

## Capabilities

### New Capabilities
- `human-in-the-loop`: Approval-request intents, the `HitlPolicy` timeout fallback (deny/drop/escalate) with stale-timer-handle rejection, and fail-closed `expires_at` enforcement in both the pipeline and the effector guard.

### Modified Capabilities
- `wire-schemas`: `ToolIntent` gains a `kind` discriminator so an approval request is distinguishable on the wire from a tool call (the effector routes it to a human queue rather than executing it); `Continuation` gains `escalations` so the escalation bound survives a suspension. Both are additive fields under the existing `state_schema_version`.

## Impact

- **New code:** `src/beam_agents/hitl.py` (`HitlPolicy`, `Deny`/`Drop`/`Escalate`, `FallbackContext` routing, `intent_expired`/`refuse_expired`).
- **Modified code:** `core/dofn.py` (`on_hitl` policy dispatch + stale-handle guard, `_resume` expiry refusal, `_commit` deadline reconciliation, `REASON_HITL_TIMEOUT`), `core/context.py` (`request_approval` on both contexts, `act` expiry on `AgentContext`, step-index seeding), `core/loop.py` (effective deadline = min of timeout and staged expiries), `core/agent.py` (`FallbackContext` gains `kind`/`deadline_ms`/`fired_at_ms`/`pending_intent_ids` — it exists today and is unused), `core/transform.py` (`AgentConfig.hitl_policy` + validation), `testing/chaos.py` (its `_commit` monkeypatch mirrors the real signature).
- **Schemas:** `protos/beam_agents.proto` + regenerated `_pb2` (must be diff-clean in CI); golden-blob compat test extended for both new fields.
- **Public API:** `HitlPolicy` and its route types are re-exported from `beam_agents/__init__.py`; `HITL_TIMEOUT_OUTPUT` keeps its current value as the default `Deny` payload, so existing behavior is unchanged for a caller that configures nothing.
- **Tests:** unit + streaming `TestStream` scenarios (timer-first, approval-first, stale handle, both-layer expiry refusal) run offline with no docker; a `semantics and not integration` gate covers fail-closed behavior under a chaos-forced bundle retry. `core/dofn.py` and `core/context.py` are under the mutation gate, so the ceilings in `mutation-baseline.toml` need re-checking after implementation.
- **Downstream:** the effector service consumes `ToolIntent.kind` to route approvals; it is still out of scope here — this change ships only the pure guard it will call.
