## Why

`project.md` names "effectively-once end-to-end (induced worker kills: exactly one execution per `intent_id`)" as a release-blocking `-m semantics` gate, and correctness invariants #2 and #5 stake the product's entire claim on it. What exists today verifies each half in isolation and neither together: `tests/semantics/test_retry_determinism.py` proves the *pipeline* re-mints byte-identical intents under a forced bundle retry (DirectRunner, offline); `tests/semantics/test_effector_effectively_once.py` proves the *effector* collapses a replayed `intent_id` under simulated kills (in-memory transport, in-memory dedup, `BaseException` standing in for SIGKILL). Nothing has ever run the closed loop — real Kafka, real Redis dedup, a real distributed runner, real killed OS processes — and nothing has ever run it at a volume where a one-in-a-thousand duplicate would show up. The two properties that matter most to a user putting money-moving tools behind this runtime (a charge fires once; a pending approval is never silently dropped) are, end to end, untested. This change builds that gate.

## What Changes

- **Extend the local stack for a real distributed run.** Add a Beam Flink job server service to `docker/compose.yaml` (pinned by digest, alongside the existing Flink 1.19 job/task managers), so a Python `RunAgent` pipeline can be submitted to the mini-cluster over the portable runner with checkpointing enabled — the first time any test in this repo exercises a runner other than Direct.
- **Add an end-to-end chaos harness** (`tests/semantics/_e2e/`, test-only, never re-exported): topic/consumer-group provisioning per run; a supervisor that launches and `SIGKILL`s real `beam-agents-effector` worker processes; kill injectors for the Beam SDK worker and the Flink TaskManager; a deliberately **at-least-once outbox producer** that publishes each intent to Kafka once or twice (manufacturing the duplicate sink writes the gate must tolerate); and a **Redis execution ledger** the test tool `INCR`s per `intent_id`, so "how many times did the effect actually happen" is measured at the side effect itself rather than inferred from message counts.
- **Add the gate** `tests/semantics/test_effectively_once_e2e.py`, marked `semantics` + `integration` + `slow`: drive **10,000 events** through Kafka → `RunAgent` on the Flink mini-cluster → intents topic → a pool of effector workers with Redis dedup → results/approvals topics → re-injection, while killing workers at randomized intervals throughout. Assert: **effectively-once execution per `intent_id`** (ledger: zero lost effects; duplicates only within the SIGKILL crash window between a tool's effect and its durable completion record, quantitatively bounded — strict exactly-once with zero kills), **zero lost approvals** (every `APPROVAL` intent yields at least one approval message and exactly one resumed terminal decision, with no key left stranded), every duplicate delivery producing byte-identical terminal `ToolResult`s, every committed `intent_id` equal to `intent_id_for(entity_key, seq, step_index)` across checkpoint restore, and full accounting of all 10,000 events (executed or explicitly refused — never silently dropped).
- **Tighten the docker semantics selection.** `make test-semantics` becomes `-m "semantics and integration"` so the docker lane runs the docker-backed gates (rather than re-running the offline ones) and still fails on an empty collection; `integration.yml` gains the job-server wait and a raised `timeout-minutes` budget for the 10k run. Both semantics selections together cover every `semantics`-marked test, so no gate can fall between them.
- **Document the substitution at the outbox hop.** `WriteIntents(kafka://…)` is upstream-broken (`tests/actions/test_write_intents_integration.py` — Beam 2.60–2.72 leaks a Java-native `kafka_write:v2` urn into the cross-language expansion response). The gate therefore publishes `.intents` through the harness's own at-least-once producer rather than the real Kafka writer, and records that as an explicit, closable gap.

## Impact

- **Depends on** the stateful `_AgentDoFn` runtime (C09), `agent-context`'s deterministic `intent_id_for`, the reference effector (`effector-service`/`effector-dedup`/`effector-execution`, including its publish-then-commit at-least-once ordering, lease-expiry recovery, and Redis dedup store), `hitl.py`'s approval path, and `WriteIntents`' key/serialization conventions. The gate is a pure verifier: it adds no production mechanism and changes no production module.
- **New code:** `tests/semantics/_e2e/` (harness package: `stack.py` topic/consumer-group provisioning, `workers.py` effector process supervisor, `chaos.py` kill injectors, `ledger.py` Redis execution ledger, `outbox.py` at-least-once producer sink, `agent.py` the module-level test agent) and `tests/semantics/test_effectively_once_e2e.py`. No changes under `src/beam_agents/` — a failure here is a real defect in the runtime or effector, never in the gate's own plumbing. **One recorded exception (design F11):** the gate's first execution exposed a launch-blocking bug in `effector/__main__.py` (service built outside the event loop, crashing every real-transport startup), fixed minimally in this change with a pinned regression test in `tests/effector/test_main.py`.
- **Infrastructure:** `docker/compose.yaml` gains a `flink-jobserver` service (digest-pinned) and `docker/README.md` gains its port row and a note that the Flink path is exercised only by this gate. Compose remains untouched by the offline lanes.
- **CI/build:** `Makefile`'s `test-semantics` narrows to `-m "semantics and integration"`; `.github/workflows/integration.yml` waits on the job server and raises `timeout-minutes` to accommodate the 10k run; `project.md`'s testing-tier note records that the effectively-once end-to-end gate now exists and is docker-backed. The gate is release-blocking and MUST NOT be marked `xfail`, `skipif`, or flaky-tolerant.
- **Dependencies:** no new third-party runtime dependencies. The `integration` dependency group already ships `aiokafka`, `redis`, and `testcontainers`; the gate additionally needs the Flink job server image (docker only) and Beam's `PortableRunner`, both already available through `apache-beam[gcp]`.
- **Runtime cost:** this is the most expensive check in the repo — a real cluster, real brokers, 10k events, repeated process kills. Budgeted at ≤ 15 minutes wall clock inside the integration workflow, with the volume tunable by env var for local iteration but pinned at 10,000 in CI.
- **Known gap (explicit, closable):** the real `WriteIntents` Kafka writer is not in the loop, because it is upstream-broken; its Pub/Sub path stays covered by the existing integration test, and the Kafka path re-enters this gate once Beam ships the fix.
