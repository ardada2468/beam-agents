## Context

The effectively-once claim has two halves and this repo currently proves each one alone, in a laboratory:

- **Pipeline half** — `tests/semantics/test_retry_determinism.py` forces one commit to fail and shows the replayed activation re-mints a byte-identical intent and pays nothing extra to the provider. DirectRunner, single process, `FakeLLM`, no broker.
- **Executor half** — `tests/semantics/test_effector_effectively_once.py` replays an intent stream with a `BaseException` raised at each phase boundary and shows the effector collapses duplicates on `intent_id`. In-memory source, in-memory sink, `InMemoryDedupStore`, single process.

Both are valuable and neither is end-to-end. A `BaseException` at a named phase is a *model* of a SIGKILL, not a SIGKILL: it cannot produce a half-written Kafka batch, a consumer-group rebalance under a dead member, a Redis claim stranded by a lease, or a checkpoint restore that replays a window of activations. And nothing has run at a volume where a rare interleaving surfaces — the existing gates run single-digit intents. `project.md` promises the real thing ("effectively-once end-to-end (induced worker kills: exactly one execution per intent_id)"), lists it as release-gating, and it does not exist.

Four properties of the existing system shape the whole design:

1. **Everything downstream of the effector is at-least-once by construction.** `EffectorService._execute` stores the result durably (`dedup.complete`), *then* publishes, *then* commits the offset — so a kill between publish and commit necessarily republishes. Any assertion that counts messages is therefore wrong by design. Executions must be counted at the side effect.
2. **Recovery from a kill is lease-driven, not handback-driven.** `_release_claim` deliberately does *not* hand back a claim whose tool may have run; the claim is recovered by lease expiry. So a "kill" injected into the gate must be followed by real elapsed time (lease TTL) before the work can be retried — the gate's own pacing is bounded below by `lease_ms`.
3. **`WriteIntents(kafka://…)` is upstream-broken.** `tests/actions/test_write_intents_integration.py` root-causes it in detail: Beam 2.60–2.72's `KafkaIOTranslation$WriteRegistrar` leaks a Java-native `beam:transform:org.apache.beam:kafka_write:v2` urn into the cross-language expansion response, and `PTransform.from_runner_api` has no generic-composite fallback for an unrecognized non-empty urn. The test is `xfail(strict=False)`. The pipeline→outbox hop therefore cannot use the production Kafka writer today.
4. **No test in this repo has ever used a runner other than Direct.** The compose stack ships a Flink 1.19 JobManager/TaskManager pair that nothing submits to; there is no Beam job server, and `flink` appears in the codebase exactly once, in a pytest marker description.

The gate is a pure verifier: it adds no production mechanism, and a failure in it is a defect in the runtime or the effector, never in the plumbing.

## Goals / Non-Goals

**Goals:**
- Run the closed loop on live services — real Kafka, real Redis, real effector *processes*, a real distributed runner — and kill real processes in the middle of it.
- Assert the two properties a user putting a money-moving tool behind this runtime actually cares about, at 10,000 events: a charge fires exactly once, and a pending approval is never silently dropped.
- Measure executions at the side effect, and tolerate duplicate messages everywhere, because at-least-once delivery is the design, not a bug.
- Make it release-gating: docker semantics selection, no `xfail`, no `skipif`, no flake tolerance, non-empty collection enforced.

**Non-Goals:**
- Proving the production `WriteIntents` Kafka writer end to end — blocked upstream (context §3). Its Pub/Sub path stays covered by the existing integration test; the Kafka path re-enters this gate when Beam ships the fix.
- Any production code change. Kills are injected from outside the process; ledgering and duplicate publication live entirely in the harness.
- Real LLM providers (`FakeLLM` throughout), Dataflow (nightly `-m dataflow`), or the state-compat golden-blob gate (a separate `-m semantics` change).
- A throughput or latency benchmark. The volume exists to expose rare interleavings, not to measure speed; the p50/p99 budget is benched elsewhere.

## Decisions

### D1: Kills are real signals to real processes, never in-process exceptions
The effector runs as N separate `beam-agents-effector` subprocesses launched by the harness supervisor (`tests/semantics/_e2e/workers.py`) sharing one consumer group, and a kill is `os.kill(pid, SIGKILL)` — no shutdown handler runs, no claim is handed back, and recovery goes through lease expiry and consumer-group rebalance exactly as it would in production. The service already supports this shape: `__main__.py` takes every setting from flags/env and `serve()` installs SIGINT/SIGTERM handlers that SIGKILL deliberately bypasses.
- *Alternative — reuse the in-process `RecordingDedupStore(crash_after=…)` model from the offline gate:* rejected. It is the thing this change exists to go beyond; it cannot produce a rebalance, a stranded lease, or a partially-flushed producer batch.
- *Consequence:* the supervisor owns cleanup (kill every child on teardown, including on assertion failure or timeout) via a session fixture with `finally`-guaranteed teardown, so a failed gate never leaks processes into the next test.

### D2: The pipeline runs on the Flink mini-cluster via a job server, with an environment that yields killable workers
Add `flink-jobserver` (`apache/beam_flink1.19_job_server:2.72.0`, matching the `apache-beam` pin in `uv.lock` and the compose Flink 1.19 images, digest-pinned like every other service) submitting to the existing `flink-jobmanager`/`flink-taskmanager` pair. The pipeline is submitted with `PortableRunner --job_endpoint=localhost:<jobserver>`, checkpointing enabled, and a fixed-delay restart strategy so a killed worker restores from the last checkpoint instead of failing the job.

The SDK environment is the open question, and the choice is ranked with an explicit fallback because it interacts with cross-language `ReadFromKafka` (which needs a Java SDK harness) and with docker-in-docker on GitHub runners:

1. **Preferred — `--environment_type=DOCKER`**, docker socket mounted into the TaskManager. Satisfies the Java environment cross-language `ReadFromKafka` requires *and* gives individually-killable SDK harness containers, so "kill a pipeline worker" is `docker kill <sdk-harness>`.
2. **Fallback — `--environment_type=EXTERNAL`** with a Python SDK harness as its own compose service (killable container, no docker socket needed), and the ingest hop narrowed: events are pre-published to Kafka by the harness and read into the pipeline by a plain consumer feeding a `TestStream`/`Create`, dropping cross-language `ReadFromKafka` from the loop. This keeps every property the gate exists for and loses only "the production Kafka reader was in the loop" — recorded in the same gap note as the `WriteIntents` substitution.
3. **Rejected — `--environment_type=LOOPBACK`.** The SDK worker would run inside the pytest process, making a pipeline-worker kill impossible; the gate would silently degrade to the offline gate with extra infrastructure.

**Task 1 is a spike that picks between 1 and 2 on GitHub's runner, not on a laptop** — that is where docker-in-docker and the 2-core/7 GB budget actually bite. Whichever wins, the fault injector that always works is the **TaskManager container kill** (`docker kill flink-taskmanager` + restart), which is a genuine distributed-worker kill independent of environment type; it is the primary pipeline-side injector and the SDK-worker kill is the additional case.

### D3: Executions are counted at the side effect, in Redis — never by counting messages
The test tool is a `side_effect=True` tool whose body does one `INCR` against a run-scoped Redis hash keyed by `intent_id`, then returns a deterministic receipt. The gate's central assertion is `max(counts) == 1 and min(counts) == 1` over all minted `intent_id`s. This is the only measurement that means what the invariant says: per context §1, results and approvals *will* arrive more than once, and an assertion over message counts would either fail on correct behavior or be weakened until it proves nothing.
- *Alternative — count `ToolResult`s on the results topic:* rejected; publish-then-commit guarantees duplicates. Those duplicates are instead asserted to be byte-identical (a separate, weaker but real property).
- *Alternative — read the effector's `CountingMetrics`:* rejected; the metrics live inside processes the gate deliberately kills.

### D4: The outbox hop uses a harness at-least-once producer, and the substitution is documented as a closable gap
`.intents` is published to the intents topic by `tests/semantics/_e2e/outbox.py` — a `beam.DoFn` producing in `finish_bundle` — rather than by `WriteIntents`, because the production Kafka writer is upstream-broken (context §3). The producer is *deliberately* at-least-once: it publishes a seeded fraction of intents twice. That is not a compromise, it is the requirement — the gate must manufacture duplicate sink writes, and a producer that duplicates on purpose is a more reliable source of them than hoping a kill lands in the right microsecond.
- *Alternative — route the outbox through the Pub/Sub emulator, whose `WriteIntents` path passes today:* rejected. Beam's Python Pub/Sub IO is Dataflow/Direct-only and is not supported on the Flink portable runner, so it cannot coexist with D2; and Kafka is the transport the effector's ordering guarantees are documented against.
- *Gap note:* `docker/README.md` and the gate's module docstring record that the real `WriteIntents` Kafka writer is out of the loop, with a pointer to the upstream root cause, so the substitution is visible rather than assumed.

### D5: Approvals are closed by a harness feeder, and "lost" is defined by a balance, not a sample
A feeder task consumes the approvals topic and publishes a decision back onto the approvals topic for re-injection on the same key. "Zero lost approvals" is asserted as a **balance over the full population**: `|approval-bearing keys admitted| == |keys that reached exactly one terminal decision on .output|`, where a terminal decision is an approved/denied outcome *or* a fail-closed HITL-timeout fallback. A late decision (deadline already passed, timer already fired) must show up on `.errors` as `orphaned_result` — the fallback stands, the late approval is surfaced, nothing vanishes. Deliberately including the timeout path in "terminal" is the point: invariant 6 says a missed approval fails closed, and a gate that only accepted approvals-that-arrived would call correct fail-closed behavior a loss.

### D6: All assertions are made from outside the pipeline, after the run drains
The gate reads the intents/results/approvals topics with a plain `aiokafka` consumer and the ledger with a plain Redis client, after driving the run to quiescence. Nothing is asserted through a shared object read across Beam's serialization boundary — the same lesson `add-retry-determinism-gate` D4 recorded after a spike gave nonsensical `FakeLLM.call_count` values through a pickled DoFn, made worse here by processes that are killed mid-run. Quiescence is detected by "no new offset on any topic for a settle window, and every minted `intent_id` accounted for", under a hard deadline — never by a fixed `sleep`.

### D7: Volume is pinned at 10,000 in CI and tunable downward only locally
`BEAM_AGENTS_E2E_EVENTS` (default 10,000) lets a developer iterate at 200; CI never sets it, so the gate runs the full population. Budget: ≤ 15 minutes wall clock, enforced by `@pytest.mark.timeout(...)` overriding the global 30 s, with `integration.yml`'s `timeout-minutes` raised from 30 to accommodate it alongside the existing integration suite. The kill schedule is randomized but **seeded and logged** — a failure must be replayable from its seed, or a release-gating chaos test becomes an unactionable flake generator. Kills are triggered by **run progress** (seeded fractions of expected ledger executions), not wall clock: a time-based schedule either misses a fast run entirely or bunches into a slow run's tail (observed in the first live run — 0/3 kills fired before quiescence), and the gate asserts every scheduled kill actually executed, so timing variance must not be able to skip the chaos.

### D8: The docker semantics selection is narrowed so the two lanes partition the tier
`make test-semantics` becomes `-m "semantics and integration"` (today: bare `-m semantics`, which re-runs the offline gates inside the docker lane for no added signal and would let this gate hide among them). With `test-semantics-offline` already selecting `-m "semantics and not integration"`, the two selections partition the tier exactly — a task asserts this by enumerating collected node ids under both selections and checking the union equals bare `-m semantics` with an empty intersection, so a future gate cannot escape both lanes.

## Risks / Trade-offs

- **[R1] Flakiness is the existential risk.** A release-gating chaos test that fails once a fortnight for infrastructure reasons gets `xfail`ed, and then the invariant is unguarded again — worse than not having the gate. → Mitigations, all mandatory: no `sleep`-based correctness (quiescence is offset-driven under a deadline); seeded, logged randomness so any failure is replayable; lease/TTL/deadline constants chosen with explicit headroom over the injected kill schedule (context §2 — recovery cannot be faster than `lease_ms`); the harness distinguishes *infrastructure* failure (a service never became healthy, the job never reached RUNNING) from *invariant* failure and reports them differently, so a broken runner is never misread as a correctness regression. A first-week flake budget of zero: any flake found during implementation is root-caused, not retried.
- **[R2] Docker-in-docker for `environment_type=DOCKER` may not be workable on GitHub runners** (socket permissions, image pulls inside the TaskManager, memory). → Mitigation: D2's ranked fallback to `EXTERNAL` with a narrowed ingest hop; task 1 spikes this on CI hardware before anything else is built, so the answer is known before the harness is written against it.
- **[R3] Resource ceiling.** Redpanda + Redis + Flink JM + TM + job server + SDK harnesses + 10k events on a 2-core/7 GB standard runner is close to the edge; an OOM-killed container reads as a mysterious gate failure. → Mitigation: pin per-service memory in compose, keep the agent trivially cheap (one `FakeLLM` step, one intent), assert on the job's own health as a precondition, and surface container exit codes in the failure message. If the ceiling is genuinely hit, the escape hatch is a larger runner for the `integration` workflow — not a smaller event count.
- **[R4] The real `WriteIntents` Kafka writer is not in the loop** (D4), so a regression in the production writer's key/serialization would not be caught here. → Mitigation: the existing unit suite (`tests/actions/test_write_intents.py`) covers the writer's key and coder shape with fake writers, the harness producer sets the message key exactly as `WriteIntents` sets it (raw `entity_key`), and the gap is written into the docstring with the upstream pointer so it closes rather than calcifies.
- **[R5] First use of a non-Direct runner in the repo** means unknown-unknowns in how `RunAgent` behaves under Flink's state backend and checkpointing — plausibly the gate's first finding is a real runtime defect rather than a green check. → Accepted, and arguably the point: `project.md` lists Flink as a v1.0-supported runner and nothing has ever verified that claim. A defect found here is the gate working. Budget the implementation accordingly; a runtime fix discovered this way belongs in its own change, not folded in here.
- **[R6] 15 minutes added to every PR's integration lane.** → Accepted: this is the check that gates the product's central claim. Mitigated by running it concurrently with the existing integration suite's services (one compose bring-up) and by the local low-volume knob (D7) so contributors are not paying it during iteration.

(1) Spike the D2 environment choice on CI hardware; (2) add the `flink-jobserver` compose service and its README row; (3) build `tests/semantics/_e2e/`; (4) add the gate; (5) narrow `make test-semantics` and raise the integration workflow budget; (6) update `project.md` and `docs/ci.md`. ## Spike findings (task 1, resolved)

Run against the real stack (Redpanda + Redis + Flink 1.19 JM/TM + `apache/beam_flink1.19_job_server:2.72.0`), these are empirical, not predicted:

- **F1 — `RunAgent` runs on Flink.** Verified: a keyed streaming pipeline over the portable runner produced `a#0`, `a,b#1`, `c#0` for two keys — per-key ordering, memory persistence, and independent per-key `SEQ`, all on real Flink keyed state. Design R5's "the gate's first finding may be a runtime defect" did not materialize for the core runtime.
- **F2 — D2 option 2 (`EXTERNAL`) wins; option 1 (`DOCKER`) is not viable here.** The stock Flink image has no `docker` CLI and no socket, so `DockerEnvironmentFactory` fails with `Cannot run program "docker"`. Option 1 would need a custom *TaskManager* image plus a host socket mount, on top of the SDK image F4 requires anyway. `EXTERNAL` needs one image and no privileged access.
- **F3 — the SDK harness must share the TaskManager's network namespace.** Beam hands the external worker pool the TM's endpoints as `localhost:<port>`; on a separate network the TM logs `Still waiting for startup of environment` forever. `network_mode: "service:flink-taskmanager"` fixes it, at the cost of coupling: killing the TM destroys the namespace the harness borrows, so a TM kill must restart the harness too.
- **F4 — the stock SDK harness image cannot import this repo's protobuf bindings.** The committed `_pb2.py` is 6.x gencode; `apache/beam_python3.11_sdk:2.72.0` ships protobuf runtime 5.29.5, and protobuf requires a matching major version. Pinning `protobuf==6.33.6` in a derived image satisfies both sides (Beam's own requirement is `<7.0.0`, and its generated protos were verified to import under 6.33.6). This is why the harness image is built, not pulled.
- **F5 — artifact staging across containers is broken by default, and staging is the wrong mechanism anyway.** The job server writes staged artifacts to a local path and hands the TM that path; on separate filesystems the harness fails with `failed to retrieve chunk`. A shared volume fixes it, but `--extra_package` would still make every SDK worker start pay a pip install — unacceptable on the recovery path of a gate that kills workers deliberately (R1). Dependencies are baked into the image instead; the shared volume stays as a backstop.
- **F6 — the TaskManager needs a much larger metaspace.** Every portable job submission loads fresh classes; at the default 256 MiB the TM dies with `OutOfMemoryError: Metaspace` after a handful of submissions, and the *client* sees an unrelated-looking gRPC `Connection closing while performing protocol negotiation`. Raised to 1 GiB. A gate that submits and recovers jobs repeatedly would otherwise degrade mysteriously as it runs.
- **F8 — the SDK worker pool and the Flink services degrade with job-submission count, and a degraded stack mimics a correctness stall.** The stock worker pool container fails permanently ("out of retries, failing container") after a handful of SDK-worker exits — normal env teardown between jobs counts against the budget — after which every subsequent job hangs with all-zero counters and gRPC connect errors; the TaskManager additionally accumulates classloader leaks (`NoClassDefFoundError` on vendored netty inner classes) across submissions. During this spike, a dead pool produced *hours* of false "the runner can't do X" conclusions, including a false "defer_remainder doesn't resume on Flink" result reproduced twice. Consequences, all mandatory: the gate runs against freshly-restarted `flink-*`/`beam-sdk-harness` services (stack.py restarts them per run); the harness health-checks the pool before submitting (a trivial pipeline or a pool-log probe); and the infra-vs-invariant distinction (R1) is not optional reporting polish — it is the difference between a real red gate and a wasted week.
- **F9 — SDF `defer_remainder` resumption WORKS on portable Flink, and the spool source is verified end to end on the stack.** On a fresh stack, `PeriodicImpulse` delivered 90 future-dated ticks incrementally, and the spool SDF read a pre-sealed segment, tailed, picked up a segment sealed 20 s into the run, and delivered its record through the pipeline to Kafka. (An earlier contrary result was F8 in disguise.) The spool defers with an absolute wall-clock `Timestamp` and drives a `ManualWatermarkEstimator`, matching the one pattern Beam itself ships (`ImpulseSeqGenDoFn`).
- **F10 — REAL_TIME timers fire on schedule on portable Flink iff the operator's upstream is live; an idle-deferred SDF residual is not re-fired after checkpoint restore.** Verified with wall-clock-stamped emissions: a timer armed by element 1 fired 2.5 s later with no further input (upstream = the live spool source), while the identical DoFn under a bounded `Create` upstream never fired — Flink's end-of-input quiesces pending processing-time timers. Separately, a `docker kill` of the TaskManager showed the job restores keyed state from its checkpoint correctly (pre-kill outputs exactly once, no duplicates, checkpoints resume completing) but the spool SDF's idle-deferred residual is never re-fired post-restore: tailing stops. Consequences: the HITL deadline path works on Flink in the gate's real topology (live source); a timer-driven tail is impossible (bounded upstream); and pipeline-kill recovery in the gate is exercised as **cancel + resubmit with full replay from the immutable spool** (D10) rather than in-place restore-and-continue, whose source-side resume is a runner limitation worth filing upstream.
- **F11 — the gate's first execution found a launch-blocking defect in the effector CLI, fixed here as the one deliberate exception to "no src/ changes".** `main()` evaluated `build_service(...)` as an argument to `asyncio.run(serve(...))` — before any event loop exists — and the Kafka adapters construct aiokafka clients in `__init__`, which requires a running loop. Every real (non-`memory://`) deployment of `beam-agents-effector` crashed at startup; no existing test could see it because `test_main.py` mocks the constructors and the integration tests build sources inside their own async functions. Fix: construct inside the loop (`_build_and_serve`), pinned by a regression test that probes `asyncio.get_running_loop()` from a monkeypatched builder. This is exactly the class of defect the gate exists to catch — it is recorded here rather than silently folded in, and it is the only production-code change in this change.
- **F12 — the portable Flink runner's follow-up streaming submission stochastically never starts its source.** Reproduced across seeds at a ~30–50 % rate with full instrumentation: the phase-B replay job reaches RUNNING and completes checkpoints, but every vertex sits at `in=0 out=0` for minutes — `Source: Impulse` never emits its single element, the spool SDF's worker-side breadcrumb never logs, zero user code executes. Only ever observed on the second-or-later streaming submission after a TaskManager kill/recovery; the first submission of a run has never stalled. Ruled out along the way (each once suspected): the offsets probe (fixed separately — an unsubscribed aiokafka consumer has no topic metadata), phantom-TM slot allocation (an eviction wait exists now), and worker-pool budget exhaustion (the F8 reorder — a real hardening, but the stall reproduced after it). Since no user code runs, a stalled submission says nothing about replay determinism or dedup; see D11 for how the gate treats it. Worth an upstream Beam issue with the captured TaskManager thread dumps (`docker/e2e-spool/*-tm-threads.txt`).
- **F13 — the gate empirically demonstrated the crash-window duplicate: strict exactly-once at the side effect is unachievable for non-idempotent tools, by design.** A seeded run caught a SIGKILL landing between a tool's effect (the ledger INCR) and the effector's `dedup.complete`; the lease expired, another worker claimed, and the tool executed a second time — exactly the recovery `service.py` documents ("the tool may already have run… let the lease expire"). The offline effector gate never sees this because its kill points (claim/complete/publish) bracket but never bisect the invoke→complete window. This is the textbook boundary: exactly-once side effects over non-transactional, non-idempotent effects cannot survive a crash inside the effect-to-durable-record window. Everything dedupable held (zero lost effects, single stored result, no divergent outcomes). Decision (user-approved): the spec states the honest bounded claim — zero lost effects; duplicates only within the crash window, bounded by `kills × max_concurrent_partitions` with per-member cap `1 + kills`; strict exactly-once when kills = 0 — and a **separate follow-up change** passes intent identity (`IntentInfo`) to side-effect tools so idempotency-capable tools get true exactly-once, keyed on `intent_id`, which the gate will then assert in its strong form.
- **F7 — cross-language Kafka IO does not work on this stack at all.** `ReadFromKafka` through the job server's expansion service fails for the same reason as F2: the Java transform's environment defaults to `DOCKER` and the TM cannot launch it. Context §3 already ruled out the Kafka *write*; this rules out the Kafka *read* too, for a different and more fundamental reason — no Java environment exists here.

### D9: Ingest is a two-layer spool — a host-side Kafka drainer feeding an append-only file store, read by a pure-Python Splittable DoFn (resolves F7)

F7 removed cross-language `ReadFromKafka`, and the checkpoint-restore-replay requirements need a *replayable* source. Rather than reimplementing the Kafka wire protocol inside a checkpointed SDF, ingestion splits into two layers:

1. **Drainer (outside the pipeline, in the test process):** a plain `aiokafka` consumer tails the events topic *and* the re-injection topics (results, approvals) for the whole run — re-injection traffic arrives mid-run, so this is continuous, not a pre-step — appending each record as a length-prefixed serialized `AgentEnvelope` to sequence-numbered segment files on a shared bind mount. Segments are written to a `.tmp` name and sealed by atomic rename; a sealed segment is immutable forever after. At quiescence the drainer writes an EOF sentinel.
2. **Spool source (inside the pipeline):** a Splittable DoFn lists sealed segments, holds `(segment, byte offset)` in restriction state, and tails for new segments until the sentinel appears. On checkpoint restore, the restored restriction re-reads the same immutable bytes — replay is exact by construction, which is precisely what the intent-determinism assertion (spec: identical `intent_id`s across restore) requires.

Why this beats the alternatives:
- *Kafka-wire SDF (original option 1):* consumer lifecycle, rebalance, and reconnect logic inside a checkpointed DoFn is the hardest-to-get-right kind of test infrastructure, and a bug in it invalidates the gate. The spool SDF's replay story is trivial to audit.
- *SQLite / Parquet as the store:* the SDF executes inside the `beam-sdk-harness` container while the drainer runs on the host, so the store crosses a Docker bind mount (virtiofs on macOS, overlay on CI); SQLite locking across those is a known flake source (R1), and Parquet is append-hostile. Plain sealed segment files are lock-free with a single writer and any number of readers.
- *Dropping the pipeline-side kill scenarios:* would gut the half of the gate that justifies the Flink cluster.

Consequences: the compose `beam-sdk-harness` service gains a bind mount (host `docker/e2e-spool/` ↔ container `/var/beam-agents/spool`); Kafka remains in every hop (events, intents, results, approvals all traverse real topics — the spool is only how the pipeline *reads* them), and the substitution joins the same documented gap note as the outbox producer (D4). Per-key ordering: the drainer preserves per-partition consumption order within a segment stream, and the run shape keeps cross-event ordering pressure off the source by giving events distinct keys — per-key sequencing then comes only from causality (event → intent → result → resume), which is inherently ordered.

### D10: The pipeline-kill scenario is cancel-and-resubmit with full spool replay; checkpoint restore is asserted for state consistency only (resolves the F10 limitation)

F10 leaves in-place restore-and-continue unavailable (the restored source never resumes tailing), so the gate exercises the two recovery properties separately:

1. **Restore consistency:** after a TaskManager kill, the job restores from its last checkpoint and the gate asserts pre-kill work is *not duplicated* (already demonstrated in the spike: pre-kill outputs appear exactly once post-restore) — the atomic-commit/keyed-state half of the claim.
2. **Wipe-and-replay determinism:** the harness then cancels the stalled job and resubmits the identical pipeline against the same immutable spool, replaying every event from segment zero with completely fresh pipeline state. Same per-key event order → same `seq` and `step_index` derivation → byte-identical `intent_id`s; the effector's dedup collapses every replayed intent, and the ledger still shows exactly one execution per id. This is the *stronger* end-to-end statement — even total pipeline-state loss with full replay produces zero duplicate side effects — and it is precisely invariant 2's reason to exist. It also matches the operational reality of catastrophic recovery (rebuild the job, replay the log, trust determinism + dedup).

The alternative — keeping in-place restore-and-continue by hoping the kill never lands while the source is idle-deferred — was rejected: a release gate cannot depend on kill timing luck, and the runner limitation is real and documented (F10; upstream issue to file). Duplicate publications produced by replay are expected and are exactly what the byte-identical-duplicates assertion consumes.

### D11: A zero-progress replay submission is retried (bounded) and classified as infrastructure, never as a red invariant (resolves F12)

The gate's phase B submits the replay pipeline up to three times. A submission whose vertices all sit at `in=0 out=0` past a generous stall window (environment spin-up takes ~30–60 s on its own) is provably infrastructure — no user code ran, so nothing about the effectively-once claim was tested, let alone violated. Each stall is logged loudly with the per-vertex counter snapshot, a TaskManager thread dump is captured for the upstream report, and the job is cancelled and resubmitted against a fresh worker pool. Three consecutive stalls raise `InfraFailure`. This is *not* flake tolerance for the invariant: every invariant assertion (ledger exactly-once, replay adds zero executions, intent determinism, byte-identical duplicates, approvals balance) runs unchanged once a submission starts processing, and a deadline breach *after* progress began still fails the gate as a liveness/invariant problem. The line being drawn is between "the dev-stack runner failed to start a job" (retry, classify) and "the runtime misbehaved while running" (red gate) — the same line R1's infra-vs-invariant distinction has drawn all along.
