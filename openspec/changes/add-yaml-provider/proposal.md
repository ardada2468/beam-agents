## Why

A system-triggered agent pipeline is mostly plumbing: read a topic, key by entity, run the agent, drain the tagged outputs to sinks. Beam YAML expresses exactly that shape declaratively — sources, keying, external transforms, sinks — and `openspec/project.md`'s module map has reserved a `yaml/` provider package for it from the start. Today nothing fills it: `RunAgent` is reachable only from Python, because its configuration is callable-heavy where YAML can only carry scalars. An agent is an async callable satisfying the [`Agent` protocol](../../../src/beam_agents/core/agent.py:132); [`AgentConfig.provider_factory`](../../../src/beam_agents/core/transform.py:403) is a zero-arg callable returning an `LLMClient`; `hitl_policy.on_timeout`, `decode`, and `tool_registry` are callables or object instances. None of those can be written in a YAML document.

The string-friendly half already exists. The sink surface is URI-shaped by design — [`intents_to`/`traces_to`/`errors_to`](../../../src/beam_agents/core/transform.py:417) are plain strings validated by [`DefaultSinkResolver`](../../../src/beam_agents/core/transform.py:249) against the `kafka://`/`pubsub://`/`bigquery://`/`otlp://` grammars — and the runtime knobs (`activation_timeout_s`, `ttl_ms`, `cancel_grace_s`) are scalars. What is missing is a thin construction-time adapter that (1) resolves the irreducibly-Python parts from `module:object` reference strings, (2) maps a YAML-friendly config mapping onto `AgentConfig`, (3) bridges Beam YAML's schema'd rows to `RunAgent`'s `KV[bytes, AgentEnvelope]` input and proto-typed outputs, and (4) exposes the four outputs of [`RunAgentOutputs`](../../../src/beam_agents/core/transform.py:438) under Beam YAML's multi-output addressing.

## What Changes

- **New `beam_agents/yaml/` package** — the module map's reserved slot — whose public surface is one fully-qualified transform constructor (`beam_agents.yaml.run_agent`) that Beam YAML's Python provider mechanism can map a YAML transform name onto. The constructor takes only YAML-representable values (strings, numbers, booleans, mappings) and returns a `beam.PTransform` wrapping the existing public `RunAgent`; it imports nothing from `apache_beam.yaml` itself — it is consumed *by* Beam YAML, not built on it.
- **`module:object` reference resolution for agents and other callable config.** `agent: "my_pkg.agents:fraud_agent"` names a module path and an attribute, separated by a colon (the setuptools entry-point convention). References are resolved by import at transform-construction (YAML expansion) time, so a typo'd module, a missing attribute, or an object that is not an agent raises `ValueError` with an actionable message before any pipeline runs — never inside a bundle.
- **Config mapping onto `AgentConfig`.** Scalar knobs pass through; sink URIs pass through verbatim to the existing resolver grammar; `provider` is a `module:object` reference to a module-level factory/constructor, with an optional `provider_config` mapping bound as keyword arguments into a picklable zero-arg `provider_factory`; `hitl` is a nested mapping onto [`HitlPolicy`](../../../src/beam_agents/hitl.py:136) fields (with `on_timeout` optionally a reference); `decode` and `tool_registry` are optional references. Unknown keys are rejected at construction with the valid-key list in the message.
- **Row boundary adaptation.** Beam YAML pipelines carry schema'd rows, not `KV[bytes, AgentEnvelope]`. The YAML-facing transform keys and envelopes input rows itself (config names the `key_field` and `payload_field`), and converts the four outputs to schema'd rows — reusing the existing `trace_event_to_row`/`activation_error_to_row` mappers that [`core/transform.py`](../../../src/beam_agents/core/transform.py:45) already ships for the BigQuery sinks.
- **Multi-output exposure.** The wrapped `RunAgentOutputs` surfaces as named outputs `output` (main), `intents`, `traces`, `errors` so downstream YAML transforms can address the non-main streams by name; sink URIs remain the recommended YAML path for draining them.
- **Provider declaration and docs.** A documented `providers:` block for user pipelines (Python provider type, `beam-agents` package, `RunAgent` → `beam_agents.yaml.run_agent`), a packaged provider-listing file, and a complete example YAML pipeline in `docs/yaml.md` (Kafka in, `RunAgent`, intents to outbox topic).

## Capabilities

### New Capabilities

- `yaml-provider`: the Beam YAML surface for `RunAgent` — the fully-qualified transform constructor, the `module:object` reference convention and its failure modes, the YAML-config → `AgentConfig` mapping, the row/envelope boundary adaptation, multi-output addressing, and the end-to-end YAML pipeline contract with `FakeLLM`.

### Modified Capabilities

None. `run-agent-transform` is consumed unchanged through its public surface (`RunAgent`, `AgentConfig`, `RunAgentOutputs` from `beam_agents/__init__.py`); the YAML layer is a construction-time adapter in front of it, and no existing requirement moves.

## Impact

- **Depends on:** C25 (`add-0-1-0-release`, proposed in this batch). A Beam YAML provider names an installable package in its `packages:` list; at the current unpublished `version = "0.0.0"` there is nothing a user's YAML pipeline can install. Implementation is not blocked — the in-repo tests exercise the constructor and an in-process provider against the working tree — but the user-facing `providers:` block only becomes real once `beam-agents==0.1.0` is installable.
- **New code:** `src/beam_agents/yaml/__init__.py` (package docstring + the stable `run_agent` re-export), `src/beam_agents/yaml/_refs.py` (reference parsing/resolution), `src/beam_agents/yaml/_config.py` (YAML-config → `AgentConfig` mapping), `src/beam_agents/yaml/transform.py` (the wrapping PTransform and row adapters), a packaged provider-listing file, `docs/yaml.md`, and `tests/yaml/` (reference, mapping, row-boundary, and end-to-end YAML suites).
- **Modified code:** `pyproject.toml` only — test-environment dependencies for parsing/executing YAML pipelines in the e2e suite (whatever `apache_beam.yaml` needs beyond `apache-beam[gcp]`; see Open Questions) and the same per-module mypy Beam-untyped-API relaxations every other Beam-driving module carries. No `core/`, `model/`, `hitl`, or proto change; no wire or state schema movement.
- **CI/build:** the new suites run in the offline unit tier (DirectRunner, `FakeLLM`, no docker, no network); no new *runtime* dependency — `beam_agents/yaml` imports only the stdlib, `apache_beam`, and `beam_agents`' own public surface. The mutation gate is untouched (`only_mutate` is scoped to `core/`).
- **Gates:** `make lint`, `make type` (`mypy --strict`), `make test-unit` offline, coverage ratchet at or above baseline, `uv run pre-commit run --all-files`, `openspec validate add-yaml-provider --strict`.
